# IPC Protocol v1

This document explains the contract in prose. The versioned machine-readable source of truth for the replatform foundation lives in [v1.contract.json](v1.contract.json), with generated artifacts emitted under [generated/](generated/). After contract edits, run `npm run protocol:generate`; before trusting a change, run `npm run protocol:check`.

## Transport

- shell starts the engine as a supervised child process
- shell writes UTF-8 JSON lines to engine `stdin`
- engine writes UTF-8 JSON lines to `stdout`
- engine logs diagnostic text to `stderr`

Every transport message must be serialized as one compact JSON object per line.

- `engine.ping` currently accepts no parameters and returns:
  - `protocol`
  - `engineVersion`

## Message Types

### Request

```json
{ "type": "request", "id": "1", "method": "engine.ping", "params": {} }
```

### Response

Successful response:

```json
{ "type": "response", "id": "1", "ok": true, "result": { "engineVersion": "0.1.0" } }
```

Error response:

```json
{ "type": "response", "id": "1", "ok": false, "error": { "code": "UNKNOWN_METHOD", "message": "Unsupported method" } }
```

### Event

```json
{ "type": "event", "event": "engine.ready", "payload": { "protocol": "2", "engineVersion": "0.1.0" } }
```

Structured startup failure event:

```json
{
  "type": "event",
  "event": "engine.startupFailed",
  "payload": {
    "stage": "bootstrap",
    "code": "BOOTSTRAP_FAILED",
    "message": "...",
    "paths": { "logFilePath": "/logs/engine.log" }
  }
}
```

Engine exit event, raised by the shell — not the engine — when the engine process is gone (2026-09 production readiness, Slice 5). `status` is the exit code or `null`, `graceful` is true when the shell asked the engine to stop, `generation` is the launch number within this shell:

```json
{
  "type": "event",
  "event": "engine.exited",
  "payload": { "status": 1, "graceful": false, "generation": 1, "pid": 4242 }
}
```

## Lighting Fixture Catalogue Visual Snapshot

`lighting.fixtureCatalog.snapshot` returns engine-owned fixture definitions. The `definition.visual` shape is additive and currently includes:

- physical marker basis: `shape`, `widthMm`, `heightMm`, `depthMm`
- legacy render hints retained for compatibility: `beamAngleMin`, `beamAngleMax`, `fieldAngle`, `pixelLayout`
- fixture identity render hints: `symbolKind`, `symbolVariant`, `emitterLayout`, `output`, `visualConfidence`

Allowed `symbolKind` values are `panel`, `soft-mat`, `linear-bar`, `fresnel`, and `control-node`. Allowed `output.beamType` values are `wash`, `spot`, `fresnel`, `rectangle`, `glow`, and `none`. Allowed `visualConfidence` values are `verified`, `catalogue-derived`, and `fallback`.

`emitterLayout` describes catalogue-owned emitter geometry with `emitterKind`, positive `rows`, `columns`, `segments`, optional `physicalPixels`, and `direction`. `output` describes renderable output metadata with `beamType`, optional `beamAngle`, optional `fieldAngle`, and `photometricSamples`; photometric samples expose `cct`, `distanceMeters`, `lux`, `modifier`, and `source`.

React may render these catalogue fields, but fixture policy, DMX footprints, validation, persistence compatibility, and hardware behavior remain engine-owned.

## Startup Handshake

1. engine emits `engine.ready`
2. shell sends `health.snapshot`
3. shell sends `app.snapshot`
4. shell decides whether the startup target is operator UI or commissioning from `app.snapshot`
5. shell may request non-gating domain snapshots such as `commissioning.snapshot`, `lighting.snapshot`, and `audio.snapshot`
6. shell opens the operator surface only after both startup-gating snapshots succeed
7. shell fails startup if any startup step does not complete inside its watchdog window

In the current scaffold the shell still renders the runtime scaffold immediately, but the protocol and shell state machine now model this startup order explicitly.

## Dev-Only Operator Verification

The parity program uses one additive dev-only IPC method for deterministic live verification:

- `dev.parityFixture.load`

This method is not part of the user-facing product contract. It exists so the native shell can launch into engine-owned parity states and be checked in the real app, not only in fixture-level harnesses.

The handler and the bundled fixture payloads compile only into engines built with the `dev-fixtures` cargo feature (`npm run native:engine:build:dev-fixtures`). The method stays in the contract; a release engine — every current lane — answers the error code `METHOD_UNAVAILABLE` (2026-09 production readiness, Slice 1 — finding F04).

`dev.parityFixture.load` currently accepts:

- `fixtureId`: required, one of the current fixture ids below
- `replaceExistingData`: optional boolean, default `false` — without it a load answers `INVALID_PARAMS` when the saved data's setup is already complete, before anything is written; `true` loads over it. Since the new pages program's Slice 2b a load writes its settings directly, in one transaction (the setup flag as the three commissioning keys, the page to open, the fixture's own settings and, for `lighting-populated`, its rig), and an earlier load no longer counts by itself. Until then a fixture was loaded through the `db.json` import, whose gate also counted an earlier import (an earlier fixture load among them), and until Slice 2 the gate was Planning data

Successful responses return the loaded fixture metadata (`fixtureId`, `sourcePath`, `targetSurface`, `summary`) and emit `app.changed` and `commissioning.changed`. Since Slice 2b `sourcePath` names `<app-data>/parity-fixture-<id>.json`, a record of every setting the load wrote; until then it named the copy of the fixture's `db.json` the import read.

Current fixture ids:

- `lighting-populated`
- `audio-populated`
- `setup-required`
- `setup-ready`

## Native Control-Surface Bridge

The native runtime now also exposes an engine-owned local HTTP bridge for Bitfocus Companion and related control-surface tooling. This bridge is separate from the JSON-lines IPC transport above.

- default base URL: `http://127.0.0.1:38201`
- override port with `SSE_CONTROL_SURFACE_PORT`
- current bridge endpoints:
  - `GET /api/deck/context`
  - `GET /api/deck/lcd?key=...`
  - `POST /api/deck/light-action`
  - `POST /api/deck/audio-action`
- the generated Companion profile now targets this native bridge instead of the Electron web server
- `POST /api/deck/action`, the route of the PROJECTS and TASKS pages' keys, is no longer routed since Planning left the hardware link (new pages program, Slice 2): it answers `400` `Unsupported bridge endpoint: POST /api/deck/action`. The `project_nav`, `project_status`, `project_priority`, `sort_mode` and `task_nav` LCD keys answer `400` too, and `/api/deck/context` no longer carries the Planning selection
- the exported Companion profile (new pages program, D5) has two pages, LIGHTS (page 1) and AUDIO (page 2), and three triggers: the 1 s LCD poll and a page-follow trigger for each page, on the `lcd_workspace` custom variable — `lighting` brings the deck to page 1 and also refreshes the four LIGHTS LCDs (`light_nav`, `light_intensity`, `light_cct`, `scene_nav`), `audio` brings it to page 2; Setup has no page, so the deck stays where it is while Setup is open. It ships 29 custom variables (the 25 the poll refreshes and the four LIGHTS ones). The page keys only turn Companion's page and post nothing to the bridge; LIGHTS' `AUDIO >>` jumps to page 2, and AUDIO has no page key back (the deck returns to LIGHTS by following the app). CAMERAS and PROMPTER join in Part C of the program
- authentication (2026-09 production readiness, Slice 2 — F01): every request must carry `Authorization: Bearer <token>`. The token is `<app-data>/control-surface.token` — 64 hex characters the engine creates from OS randomness on the first launch of an install and reuses afterwards; `SSE_CONTROL_SURFACE_TOKEN` overrides it for lanes without touching the file. The exported Companion profile carries the token in the generic-http `header` option of every action, the LCD poll trigger included, so a profile exported before this landed is refused and must be exported and imported again.
- refusals, checked before the body is parsed: no or wrong token → `401` with `WWW-Authenticate: Bearer`; any `Origin` header → `403`; a `Host` other than `127.0.0.1:<port>` or `localhost:<port>` → `400`
- limits (F06): headers over 8 KiB → `431`; a body over 16 KiB (by declared `Content-Length`, before it is read) → `413`; a `POST` without `Content-Length`, or any `Transfer-Encoding` → `411`; a request that has not fully arrived 1 s after a worker picked it up → `408`; four worker threads with a queue of sixty-four connections (sixteen until 2026-09-22: sixteen refused part of the exported profile's once-a-second LCD poll), a connection beyond that → `503`. Refused requests are logged at most once per status per minute, and each such line counts the refusals it stands for.
- query parameters are percent-decoded (`%2F` → `/`, `+` → space) before the key lookup (F28)
- lighting keys (2026-09 production readiness, Slice 10 — F12): every `POST /api/deck/light-action` runs under the engine's lighting state lock and changes lighting state only through the functions the IPC lighting requests run — `toggleLight`, `intensityUp` / `intensityDown`, `cctUp` / `cctDown`, `resetIntensity` and `resetCct` through the fixture update, `allOn` / `allOff` through the all-power request, `recallScene` through the scene recall, `saveScene` through the scene create (the deck names the scene `Scene N`; the id follows the scene-create rule), `deleteScene` through the scene delete. The preview buffer is the one `lighting.editor.previewMode` switches on: while it is on, a key stages its change there and the light output does not move. The relative keys start from the previewed value while previewing, otherwise from the stored value with a running fade sampled at that moment. Replies of the value, all-power and recall keys carry `preview: true | false`; a value key's reply carries what was stored, which a fixture's own colour temperature range may have narrowed. The `light_intensity` and `light_cct` LCD texts show the same value and end in a third line `PREVIEW` while previewing.
- events (Slice 10): a successful `POST` raises the event the matching IPC request would — `lighting.changed { reason: "control-surface" }` from `/api/deck/light-action`; `/api/deck/audio-action` raises `audio.changed { reason: "control-surface" }` as before. A refused action and every `GET` raise nothing.
- `switchToDeckMode`, which the page keys posted until Slice 2 of the new pages program, is refused on both routes with `501` (`Unsupported lighting deck action: switchToDeckMode`, `Unsupported audio deck action: switchToDeckMode`) and stores and raises nothing: the deck mode was a Planning setting that nothing read, and the deck follows `shell.workspace`. A profile exported before Slice 2 gets these refusals from its page keys, and `400` from its PROJECTS and TASKS keys, until the new profile is imported with Full Reset & Import
- action log (Slice 11 — F30): a successful key that changed what a device receives leaves a row with the source `deck` in the transaction that stamps the bridge's last event, so a key waits for the disk no more often than before — `allOn` / `allOff`, `toggleLight`, `resetIntensity`, `resetCct`, `recallScene`; `recallSnapshot`, `dialPress` (the mute), `dimToggle`, `soloClearAll` when something was soloed, and the first `talkOn` and the `talkOff` of a held TALK key. A dial detent (`dialTurn`, `intensityUp` / `intensityDown`, `cctUp` / `cctDown`), a selection, the bank, the dial mode and a key staged in the preview leave none (the page keys post nothing). Two replies grew for it: the lighting value keys' `light` carries `name` beside `id`, and `talkOn` / `talkOff` carry `changed` (Companion repeats `talkOn` while the key is held; only the press and the release change anything).

## Startup Lifecycle States

The shell startup state machine currently uses these lifecycle states:

- `idle`
- `launching-process`
- `waiting-for-ready-event`
- `waiting-for-health-snapshot`
- `waiting-for-app-snapshot`
- `ready`
- `failed`

Contract rules:

- `engine.ready` means the engine process is alive, storage bootstrap completed, and the protocol version is compatible enough to continue startup.
- `health.snapshot` provides operational readiness and diagnostics metadata.
- `app.snapshot` provides engine-owned shell state, UI-routing state, and startup gating data such as workspace/window restoration, commissioning status, and startup target surface.
- `app.changed` is a non-startup domain event used to tell the shell that app-owned routing or commissioning state mutated and snapshots should be refreshed. With `reason: "health"` it reports a change in the engine's health status (2026-09 production readiness, Slice 8): a subsystem in `health.snapshot`'s `checks.engine` changed state — the Stream Deck bridge port, a TotalMix meter port, the light-output socket, the database backups or the storage check. It is raised on a change of state only, never for a first `ok` and never for a repeated state. Since the new pages program's Slice 5a it is also raised after a `prompter.*` request that changed `checks.prompter` (Teleprompter › The Prompter XL).
- `commissioning.changed` is a non-startup domain event used to tell the shell that commissioning probe/config state mutated and snapshots should be refreshed.
- `lighting.changed` is a non-startup domain event used to tell the shell that lighting state mutated and snapshots should be refreshed. With `reason: "control-surface"` a Stream Deck lighting key changed it — or the preview buffer — through the local bridge (Slice 10).
- `prompter.changed` (new pages program, Slice 4) says the Teleprompter changed: `{ reason, anchor }`, where `anchor` is the glass's motion from now on (see "Teleprompter" below) or `null` when nothing is on the prompter. Every `prompter.*` request that changes something raises it with its reason; `reason: "at-end"` says the text stopped at `END`, raised by whoever finds it there first — the prompter's clock, or any request, a read or a refused one included, before its own answer — and an applied archive restore raises `reason: "backup-restored"`. A read raises nothing else.
- `audio.changed` is a non-startup domain event used to tell the shell that discrete audio state mutated and snapshots should be refreshed. It is emitted for gain/EQ/dynamics/sends/snapshot recall, transport config, clip clear, and other command results, not for high-frequency meter frames.
- `audio.meters` is the high-frequency compact meter feed. Shells must update their meter frame path only and must not refresh `audio.snapshot` for every meter frame. The current compact telemetry payload fields are:
  - `sequence`: monotonically increasing meter-frame number for the current engine process.
  - `monotonicTimestampMs`: monotonic milliseconds since the meter publisher started.
  - `cadenceHz`: intended publication cadence for the compact meter stream.
  - `meteringSource`: `rme-totalmix-osc`, `simulated`, or `disabled`.
  - `meteringState`: `live`, `stale`, `offline`, `simulated`, or `disabled`.
  - `lastPacketAgeMs`: age of the most recent live RME OSC meter packet, or `null` for simulated/disabled metering.
  - `diagnostics`: packet counters and mapping diagnostics, including packet count, mapped packet count, unknown packet count, last received OSC address, and mapped entry count.
  - `selectedMixTargetId`: active mix target id.
  - `channels`: channel meter entries keyed by each entry's `id`.
  - `mixTargets`: output/mix-target meter entries keyed by each entry's `id`.
- Compact meter entries expose normalized fallback values (`meterLeft`, `meterRight`, `meterLevel`, `peakHoldLeft`, `peakHoldRight`) plus live-console dBFS fields (`levelLeftDbfs`, `levelRightDbfs`, `peakLeftDbfs`, `peakRightDbfs`, `rmsLeftDbfs`, `rmsRightDbfs`, `peakHoldLeftDbfs`, `peakHoldRightDbfs`) and status fields (`meterPoint`, `peakWarning`, `meterPointOver`, `meterPointOverLeft`, `meterPointOverRight`, `channelPathClip`, `channelPathClipHold`, `over`, `overLeft`, `overRight`, `clipHold`, `clip`). `level*Dbfs` is the preferred moving meter body; `rms*Dbfs` remains as a compatibility alias. `peak*Dbfs` and `peakHold*Dbfs` are source peak fields; the shell may render an operator-controlled display peak hold from the visible meter body. The default display range is `-60 dBFS` to `0 dBFS`; the shell keeps adjacent marks at `0`, `-6`, `-12`, `-18`, `-24`, `-40`, and `-60`, with `-18 dBFS` as the nominal operating reference.
- Production RME frames use truthful console-style `meterPoint` values: `input` for hardware input/preamp channels, `playback` for software playback channels, and `post-fader` for output/mix-target meters. The engine applies console ballistics before publishing compact frames: held peaks stay fixed for `1500 ms`, then decay at `20 dB/s`; `peakWarning` begins at `>= -3 dBFS`; `meterPointOver*`/legacy `over*` begins at `>= 0 dBFS`; and `channelPathClipHold`/legacy `clipHold` latches until `audio.clip.clear`.
- Production meter frames with `meteringSource=rme-totalmix-osc` are derived only from received RME TotalMix OSC meter packets. The engine clears/freezes meter values and reports `stale` or `offline` when packet age exceeds the live threshold; it must not substitute simulated motion.
- Simulated metering is dev/test only and requires explicit fixture/dev configuration such as `SSE_AUDIO_SIMULATED_INPUT_MODE=1`. Simulated meter frames must always identify themselves with `meteringSource=simulated` and `meteringState=simulated`.
- `settings.changed` is a non-startup domain event used to tell the shell that persisted shell settings mutated outside a direct `settings.update` request and the authoritative `app.snapshot` should be refreshed.
- `support.changed` is a non-startup domain event used to tell the shell that backup/export state mutated and support snapshots should be refreshed.
- `ready` means the shell has received both health and app snapshots, not merely that the process exists.

## Rules

- `id` is required for requests and responses
- `event` is required for events
- all payloads must be JSON objects
- unknown methods return structured errors, not crashes
- protocol version mismatch should surface as `engine.ready` incompatibility or a structured startup error
- shell provides runtime directories through environment variables before launch:
  - `SSE_APP_DATA_DIR` (when unset, the engine uses the platform's durable per-user app-data directory — the same location the shell resolves — and refuses to start when the platform provides none; never a path relative to the working directory)
  - `SSE_LOG_DIR`
  - `SSE_PROTOCOL_VERSION`
  - optional `SSE_UPDATE_REPOSITORY_PATH`
- `health.snapshot` should expose storage metadata needed for startup diagnostics:
  - schema version
  - journal mode
  - integrity-check result
- `health.snapshot` should also expose shell-ready diagnostic summary strings and a recent engine log excerpt so the recovery surface can be rendered from engine-owned data instead of shell-local file parsing
  - `recentLogExcerpt` is a string: the last 12 lines of the current `engine.log`, read from at most its last 64 KiB and never from a rotated file, so the answer costs the same whatever the log's size (2026-09 production readiness, Slice 8 — F11)
- `health.snapshot` currently returns top-level:
  - `status` — `ok` | `attention` | `warning` | `error` (Slice 8 — F14): `error` when the saved data is not usable, `attention` when a subsystem could not bind (the Stream Deck bridge port, a TotalMix meter port, the light-output socket), `warning` when the last database backup failed or is older than 48 h, `ok` otherwise; `attention` also, never worse, when the Prompter XL is in a state other than `CONNECTED` that the shell has reported (Slice 5a)
  - `startupPhase`
  - `summary`
  - `paths`
  - `details`
  - `recentLogExcerpt`
  - `checks`
- `health.snapshot` currently also includes coarse readiness checks for:
  - `checks.lighting`
  - `checks.audio`
  - `checks.controlSurface`
  - `checks.engine` (Slice 8 — F14): the engine's own health registry, one entry per subsystem that has reported — `bridge`, `osc`, `sacn`, `backups`, `storage`, `restore` — each `{ state, detail, at }` with `state` in `ok` | `attention` | `warning` | `error`, `detail` the engine's sentence and `at` the Unix seconds of the report (for `backups`, of the last copy); `status` is the worst of them
  - `checks.prompter` (the new pages program's Slice 5a): the Teleprompter's lamp — `{ ok, status, word, summary, notUpdated, screen }`, the worse of the Prompter XL's state and `NOT UPDATED` (Teleprompter, below); `null` when the prompter cannot be read (a line in the log; never a failed snapshot). Only a Prompter XL state the shell has reported raises the top-level `status`, and to `attention` at most; an unreported one and `NOT UPDATED` light the lamp only
- `engine.ready` and `health.snapshot` should expose the engine log file path for recovery tooling
- `runtime.paths` may also expose `updateRepositoryPath` when the shell or launcher knows the workstation's maintenance-tool update-repository artifact path
- `runtime.paths.exportsDir` is `<app-data>/exports`, the only place the shell writes a diagnostics export (`diagnostics-<UTC timestamp>.json`); the shell opens only paths under the app-data, logs and update-repository directories for the operator (2026-09 production readiness, Slice 4)
- bootstrap failures should emit `engine.startupFailed` with:
  - `stage`
  - `code`
  - `message`
  - planned runtime `paths`
- protocol mismatches are startup-fatal:
  - engine rejects a requested `SSE_PROTOCOL_VERSION` before emitting `engine.ready`
  - shell also fails startup if an `engine.ready` event reports a protocol different from the shell's expected version
- `app.snapshot` currently returns:
  - `runtime.protocol`
  - `runtime.engineVersion`
  - `runtime.paths`
  - `runtime.controlSurface.available`
  - `runtime.controlSurface.status`
  - `runtime.controlSurface.summary`
  - `runtime.controlSurface.baseUrl`
  - `runtime.controlSurface.port`
  - `runtime.controlSurface.error`
  - `shell.workspace`: `setup`, `lighting`, `audio` or `teleprompter` (since the new pages program's Slice 4); new saved data opens on `audio`, and a saved `planning` reads as `audio` (new pages program, D1)
  - `shell.window`
  - `shell.summary`
  - `commissioning.hasCompletedSetup`
  - `commissioning.runnerStage`
  - `commissioning.stage`
  - `commissioning.hardwareProfile`
  - `commissioning.summary`
  - `startup.targetSurface`
  - `startup.operatorUiAllowed`
  - `summary`
- `commissioning.update` currently accepts:
  - `runnerStage`: optional, one of `import`, `probe`, `map`, `verify`, `publish`
  - `stage`: optional legacy coarse stage, one of `setup-required`, `in-progress`, `ready`
  - `hardwareProfile`: optional non-empty string
  - `runnerStage` is the plan-aligned commissioning runner state for the React/Tauri shell

## Teleprompter

New pages program, Slice 4 (2026-09-27; the ledger's D20, `docs/redesign/teleprompter-2026-09.md`). The hardware link keeps the scripts and runs the prompter; the front end draws the glass — the Prompter XL's screen (its window, Slice 5b) and the page's copy of it (Slice 6), one component since Slice 5a — and measures its layout. Every `prompter.*` request runs under the prompter's own lock. A request that changes something answers and raises `prompter.changed { reason, anchor }`; a refused one changes nothing and raises nothing of its own. Every request first stops the text at `END` if it got there, and says so with `reason: "at-end"`.

**Saved data (schema 9).** `prompter_scripts` (each script's paragraphs as JSON, its name, the file it came from, when it was made and changed, its speed and its place, and when it was removed), `prompter_script_versions` (each script's last 20 texts) and `prompter_state` (one row: the look, the take's text size, and what the glass shows — the script and its text as it went on — with the revisions of that text and of the look). The live data's schema 7 goes to schema 9 in one start, behind one pre-migration copy.

**Scripts.** A script is paragraphs of runs: `{ runs: [{ text, bold, italic, underline }] }`. A line break inside a paragraph is `\n` in a run's text. A word is a run of characters that are not white space (`/\S+/gu`). A cue is text in square brackets on one line; a line that holds a cue and nothing else is a jump target, and a word that is all cue is not read aloud, so it does not count towards the pace. The place is `{ paragraph, word }`, both from 0, and `{ paragraph: <paragraph count>, word: 0 }` is the end. Every text that comes in is cleaned: U+FEFF goes, carriage returns and U+0085, U+2028 and U+2029 become `\n`, a tab becomes a space, other control characters go.

**The clock (the slice's first step, answered 2026-09-27: layout units).** The view that draws the glass reports its layout with `prompter.layout.report { layoutKey, lines: [{ paragraph, word, top, height }], endTop }`: every line's paragraph, first word, top and height in the glass's pixels at its 1,920 px width, and where the reading line stands when `END` reaches it. `layoutKey` is the prompter's current key (`g<text revision>-l<look revision>`); a report for another key answers `{ accepted: false }` and changes nothing, and one that does not fit the text on the glass is `INVALID_PARAMS`. The layout is kept in memory only and is reported again after a start. The speed in pixels a second is the pace (words a minute) times the layout's height per read word. The anchor is:

- `layoutKey`, `place` (the paragraph and the word at the reading line), `wordOffset` (how far into that paragraph the reading line stands, in words: `6.5` is halfway through its seventh word; `place.word` is its whole part), `position` (the reading line in pixels; `null` without the layout), `endPosition`, `pxPerReadWord`;
- `playing`, `atEnd`, `fromWpm`, `toWpm`, `rampMs` (0.3 s eases for play, pause and a new pace);
- `moveFromPosition` and `moveMs` (a jump's 0.2 s move on the glass; the place is the target at once);
- `ageMs`: how old the anchor was when it was sent, since the two processes share no clock.

A view draws `position(t) = min(position + pxPerReadWord · words(ageMs + t), endPosition)`, with `words(t) = (v0·t + (v1 − v0)·t²/(2r))/60` while `t < r` and `((v0 + v1)/2·r + v1·(t − r))/60` after (seconds, words a minute). A view whose layout has another key draws from `place.paragraph` and `wordOffset` — inside a line, the reading line's height is the share of the line's words it has passed — and reports its layout. The same rule carries the place from one layout to the next in the hardware link, so a new size moves the words at the reading line by less than a word. The first report for a key is the one the clock runs on; a later report for the same key (the other view's) answers `{ accepted: true }` and changes nothing. Every paragraph needs a line of its own with a height, an empty one included, or the report is refused. `native/rust-engine/src/prompter/clock/motion-cases.json` holds the cases the hardware link and the front end's copy of the formula (`frontend/packages/engine-client/src/prompter/motion.ts`) are both tested against. The prompter is paused after every start and every archive restore; it stops by itself only at `END`; a new look, a new size or an Update keeps the words at the reading line.

**Reads.**

- `prompter.snapshot` → `{ look, sizePx, glass, scripts, removed, screen }` (`screen`: the Prompter XL as last reported, Slice 5a, below): `glass` is `null` when nothing is on the prompter, else `{ scriptId, name, layoutKey, laidOut, notUpdated, speedWpm, place, paragraphCount, playing, atEnd, timeLeftSeconds, lengthSeconds, estimated, cues, anchor }` (`estimated` while the times come from the words, before a layout); `scripts` are sorted by name with numbers in their natural order and `removed` newest first, each `{ id, name, sourceFileName, paragraphCount, readWords, speedWpm, lengthSeconds, place, atEnd, createdAt, changedAt, removedAt, onPrompter }`.
- `prompter.glass.snapshot` → `{ scriptId, name, layoutKey, paragraphs, look, sizePx, anchor }`: what the glass draws. When nothing is on it, `paragraphs` is empty and `scriptId`, `name`, `layoutKey` and `anchor` are `null`; `look` and `sizePx` are always there.
- `prompter.script.snapshot { scriptId }` → `{ script, paragraphs, cues, versions }`, versions newest first (`{ id, readWords, keptAt, reason }`).

**Scripts' methods.**

- `prompter.script.import { fileName, contentBase64, updateScriptId? }`: a file the page's own file picker read (the slice's first step 2a: a name and its bytes; the hardware link reads nothing from a path). `.docx` and `.txt` are read; a `.doc`, another kind, a password-protected document, a file that is not what its name says, one over 20 MB, over 30,000 words or over 2 MB of text, and one with no text are refused as `PROMPTER_IMPORT_REFUSED` with the operator's sentence (a paste over 20 MB has a sentence of its own). Runs of spaces inside a line come in as one space, and runs of empty lines as one. Answers `{ scriptId, name, sentence }`, the sentence counting what was kept and left out (`Imported Interview intro.docx: 18 paragraphs, 1,240 words, 3 cues. Left out: 2 pictures, 1 comment. Tracked changes were taken as accepted.`). With `updateScriptId` the file's text becomes that script's, its earlier text kept as a version.
- `prompter.script.paste { html?, text? }`: what the page read from the clipboard (first step 3a), as a new script named after its first words. HTML that yields no word falls back to the plain text; a blank line in the HTML (`<br><br>`) ends a paragraph, as in a `.txt`.
- `prompter.paste.convert { html?, text? }` (Slice 6b; the operator's answer of 2026-09-27: keep the formatting): what the editor's Paste read from the clipboard, read as `prompter.script.paste` reads it — bold, italic, underline, paragraphs and headings as cues, the same fallback to the plain text — and refused as it is refused (`PROMPTER_IMPORT_REFUSED`: over the paste's 20 MB, no text, over 30,000 words, over 2 MB of text). Answers `{ paragraphs, sentence }`: `paragraphs` in the shape `prompter.script.edit` takes, for the editor to insert at its cursor and send back whole with `edit`, and the paste's sentence (`Imported the pasted text: 2 paragraphs, 7 words, 1 cue. Left out: 1 picture.`). It converts and answers: it makes no script, keeps no version, changes nothing, raises no event and is not a Recent actions row; the `edit` that follows saves the text, and a script over 30,000 words is refused there.
- `prompter.script.create { name? }` (`New script`, `New script 2`, …), `prompter.script.rename { scriptId, name }`, `prompter.script.edit { scriptId, paragraphs }` (saved as the operator types; an edit of the script on the prompter waits for `prompter.update`; over 30,000 words is `PROMPTER_SCRIPT_TOO_LONG`), `prompter.script.remove`, `prompter.script.restore` and `prompter.script.delete { scriptId }` (the script on the prompter cannot be removed: `PROMPTER_SCRIPT_ON_PROMPTER`; only a removed script is deleted for good: `PROMPTER_SCRIPT_NOT_REMOVED`), and `prompter.script.version.bringBack { scriptId, versionId }` (the current text is kept first).

**What the glass shows** (D11: replacing, updating and clearing are armed on the page).

- `prompter.putOn { scriptId, replace? }`: on a blank prompter one press; when another script is on it, `replace: true` or `PROMPTER_REPLACE_NOT_CONFIRMED`. The script comes on paused at its place, or at the top when it was left at its end. Answers `{ action: put-on | replaced, name, replacedName, sentence }`.
- `prompter.update`: the edited text goes on with the same words at the reading line; when the paragraph there was deleted the place moves to the next paragraph's start and the sentence says so. `PROMPTER_UP_TO_DATE` when there is nothing to update.
- `prompter.clear`: the glass goes black; the script keeps its place.

Each is a Recent actions row (`domain: prompter`, with the sentence). While nothing is on the prompter, `PROMPTER_NOTHING_ON` answers `prompter.play`, `prompter.pause`, `prompter.speed`, `prompter.jump`, `prompter.update` and `prompter.clear`; `prompter.textSize` and `prompter.look.update` change the look for the next script, and `prompter.layout.report` answers `{ accepted: false }`. Clear and Replace leave the script the place it was read to — where a pause's ease stops — in its own text when it was edited and never Updated.

**The take** (one press each; none starts the scroll but `prompter.play`).

- `prompter.play` (`PROMPTER_NOT_ON_GLASS` while nothing is drawn on the glass, below; `PROMPTER_AT_END` at the end, until a jump moves the place back; `PROMPTER_NOT_LAID_OUT` before a layout), `prompter.pause` (it saves the place where its 0.3 s ease stops the text). A place or a pace that cannot be saved is a line in the log, never a refused control: the take goes on and the next save tries again.
- `prompter.speed { wpm | step }`: 40–300 words a minute in steps of 5, the script's own; `step` is a number of those steps (`step: 1` is 5 words a minute faster), stopping at the ends.
- `prompter.jump { to, paragraph?, word? }`: `top` (pauses), `back` (the start of the paragraph at the reading line; from its first line, the one before), `nextLine` / `previousLine` (need the layout), `nextParagraph` (`PROMPTER_NO_PARAGRAPH` from the last paragraph), `previousParagraph`, `nextCue`, `previousCue` (`PROMPTER_NO_CUE` when there is none; a cue at the reading line is neither), `paragraph` (from 0) or `place`. A jump keeps the scroll as it was; only `top` pauses.
- `prompter.textSize { sizePx | step | standard }`: 48–160 px in steps of 4, or the look's standard; `step` is a number of those steps (`step: -1` is 4 px smaller), stopping at the ends.
- `prompter.look.update { standardSizePx?, lineSpacingPercent?, marginPercent?, textColour?, readingLinePercent?, readingLineAcross?, dimReadText?, paragraphNumbers? }`: the proposal's §4.1 ranges; the take's size follows a new standard when it was at the standard.

**The Prompter XL** (the new pages program's Slice 5a; first steps answered by the operator on 2026-09-27). Only the shell reads Windows' display configuration, so the shell reports what it found — from Slice 5b, at its start, at every change and after the hardware link restarts — and the hardware link works out the state and owns what follows from it.

- `prompter.screen.report { found, duplicated?, width?, height?, refreshHz?, windowError? }`, sent by the shell, never by the page (the shell's page request path, `engine_request`, refuses it): whether Windows sees a screen named `Prompter XL`; whether it shows a copy of another screen; its size, numbers above 0 kept in whole pixels (required when found); its refresh rate, optional, kept in whole hertz (Windows gives a fraction: 59.94 is 60); why the window on it could not open, a sentence trimmed and cut at 300 characters, ignored while duplicated. `found: false` ignores the rest, and anything else is `INVALID_PARAMS`. It answers `{ screen, paused }`. The state is `not-connected` (not found), `duplicated`, `not-showing` (a `windowError`), `low-resolution` (below 1920×1080) or `connected`, in that order. The report is kept in memory only: after every start the Prompter XL is `NOT CONNECTED` until the shell reports (first step 2), with a sentence of its own that says Windows has not reported it yet. A report the same as the last raises nothing; one that differs (its state, size, refresh rate or window reason, or the first since a start) raises `prompter.changed { reason: "screen" }`. The shell sends it at its start, after the hardware link restarts, and on every poll of Windows' display configuration (Slice 5b), so a report lost to a moment's failure is repaired by the next.
- `prompter.play` is refused as `PROMPTER_NOT_ON_GLASS` while nothing is drawn on the glass — `NOT CONNECTED`, `DUPLICATED` or `NOT SHOWING` — with a sentence for each; `LOW RESOLUTION` plays. It is checked after `PROMPTER_NOTHING_ON` and before `PROMPTER_AT_END`. A report that takes the glass away while the text scrolls pauses it (its 0.3 s ease; the place saved where the ease stops, `paused: true`), and a report that brings it back leaves it paused (D12). Jumps, speed, the text size, the look and edits keep working.
- `prompter.snapshot` carries `screen`: `{ state, word, tone, reported, draws, width, height, refreshHz, windowError, sentence }`, the words `CONNECTED`, `NOT CONNECTED`, `DUPLICATED`, `LOW RESOLUTION` and `NOT SHOWING`, the tone `ok`, `attention` (`LOW RESOLUTION`) or `error`.
- `health.snapshot`'s `checks.prompter` is `{ ok, status, word, summary, notUpdated, screen }`: the worse of the screen's state and `NOT UPDATED` (first step 3; at the same tone `NOT UPDATED` wins over `LOW RESOLUTION`), the word and the sentence of that state, whether the script on the glass was edited after it went on, and `screen` as above. Only a Prompter XL state the shell has reported counts toward the whole `status`, and as `attention` at most (first step 1, and the operator's answers after CI's qualification lane and at the review): an unreported Prompter XL and `NOT UPDATED` light the lamp only. When one counts, the top-level `summary` ends with `Prompter: ` and its sentence. After a request that can change the check (`prompter.screen.report`, `putOn`, `update`, `clear`, `script.edit`, `script.rename`, `script.import`, `script.version.bringBack`) and did, or whose check could not be read, `app.changed { reason: "health" }` follows the request's own `prompter.changed`, so the header's lamp follows. A take's controls never read it, and it never fails a request.

## Ownership

- The shell owns process supervision, retry behavior, and desktop presentation.
- The engine owns persisted application state, commissioning state, and UI-routing decisions derived from persisted state.
- React does not issue raw protocol messages directly. All transport calls go through shell-side adapter methods.
- The shell may cache snapshot data for rendering, but the engine remains the source of truth.

## Versioning

- Additive changes inside existing result objects are allowed in protocol v1 if old clients can ignore the new fields safely.
- Removing fields, changing field types, or changing startup sequencing requires a protocol version bump.
- Protocol 2 (2026-09, the new pages program's Slice 2): Planning's methods, its event, its fixture ids and its snapshot fields are removed, and the backup archive format moves to 5. The contract and this document keep their `v1` file names; the version they carry is `2`. A window and a hardware link of different versions stop at the start with `PROTOCOL_MISMATCH`. Protocol 2 also removes `storage.importLegacyDb` and the `legacy-db-json` restore source (the new pages program's Slice 2b, 2026-09-25 — D3): protocol 2 had not shipped, so the removal rides in it rather than in a protocol 3.
- A new startup-critical method required for shell boot must be documented in the startup handshake and treated as part of the versioned contract.

## Error Taxonomy

Structured errors and startup failures should use stable codes grouped by responsibility:

- startup:
  - `BOOTSTRAP_FAILED`
  - `STORAGE_CORRUPT` (the database failed its integrity check or is not a database; the message names the file and the newest database backup; the file is left untouched)
  - `STORAGE_MIGRATION_FAILED` (a schema migration refused a stored value it could not read; nothing was changed and the pre-migration backup is on disk)
  - `ENGINE_ALREADY_RUNNING` (another engine holds the exclusive lock on `<app-data>/engine.lock`; the second engine exits before it opens the database — 2026-09 production readiness, Slice 5)
  - `STARTUP_TIMEOUT`
  - `HEALTH_SNAPSHOT_FAILED`
  - `APP_SNAPSHOT_FAILED`
- process supervision:
  - `PROCESS_ERROR`
  - `PROCESS_EXIT`
  - `ENGINE_BINARY_MISSING`
  - `ENGINE_NOT_RUNNING`
  - `ENGINE_EXITED` (answered by the shell to every request still waiting when the engine process exits; the front-end shows the recovery surface and restarts the engine on its own, at most three times in five minutes — Slice 5)
- protocol:
  - `UNKNOWN_METHOD`
  - `INVALID_PARAMS`
  - `INVALID_ENGINE_MESSAGE`
  - `PROTOCOL_MISMATCH`
- persistence:
  - `STORAGE_ERROR`
  - `RUNTIME_DIRECTORY_ERROR`
- import: none since the new pages program's Slice 2b retired `storage.importLegacyDb`, which answered `IMPORT_SOURCE_NOT_FOUND`, `IMPORT_FAILED` and `IMPORT_REQUIRES_FORCE`
- lighting:
  - `LIGHTING_UNCONFIGURED`
  - `LIGHTING_NOT_VERIFIED`
  - `LIGHTING_PROBE_FAILED`
  - `LIGHTING_SCENE_NOT_FOUND`
  - `LIGHTING_SCENE_RECALL_FAILED`
- teleprompter (new pages program, Slice 4):
  - `PROMPTER_SCRIPT_UNKNOWN`, `PROMPTER_SCRIPT_REMOVED`, `PROMPTER_SCRIPT_ON_PROMPTER`, `PROMPTER_SCRIPT_NOT_REMOVED`, `PROMPTER_SCRIPT_TOO_LONG`, `PROMPTER_VERSION_UNKNOWN`, `PROMPTER_IMPORT_REFUSED`
  - `PROMPTER_NOTHING_ON`, `PROMPTER_ALREADY_ON`, `PROMPTER_REPLACE_NOT_CONFIRMED`, `PROMPTER_UP_TO_DATE`, `PROMPTER_AT_END`, `PROMPTER_NOT_LAID_OUT`, `PROMPTER_NO_CUE`, `PROMPTER_NO_PARAGRAPH`

## Design Notes

- JSON Lines is chosen for v1 because it is easy to debug and cross-platform over a supervised child-process boundary
- if binary framing is needed later, preserve the message schema and swap only the framing layer
- the shell should treat `engine.ready` as "process is alive and protocol-compatible", not as "system is fully healthy"
- the engine should bootstrap storage paths before emitting `engine.ready`, so first-launch storage failures are caught before the shell proceeds
- `app.snapshot` is the first non-shell UI-driving contract and exists specifically to keep commissioning/dashboard routing out of ad hoc shell state
