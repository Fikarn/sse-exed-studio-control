# IPC Protocol v1

This document explains the contract in prose. The versioned machine-readable source of truth for the replatform foundation lives in [v1.contract.json](v1.contract.json), with generated artifacts emitted under [generated/](generated/). After contract edits, run `npm run protocol:generate`; before trusting a change, run `npm run protocol:check`.

## Transport

- shell starts the engine as a supervised child process
- shell writes UTF-8 JSON lines to engine `stdin`
- engine writes UTF-8 JSON lines to `stdout`
- engine logs diagnostic text to `stderr`

Every transport message must be serialized as one compact JSON object per line.

- `engine.ping` currently accepts no parameters and returns:
  - `protocol`
  - `engineVersion`

## Message Types

### Request

```json
{ "type": "request", "id": "1", "method": "engine.ping", "params": {} }
```

### Response

Successful response:

```json
{ "type": "response", "id": "1", "ok": true, "result": { "engineVersion": "0.1.0" } }
```

Error response:

```json
{ "type": "response", "id": "1", "ok": false, "error": { "code": "UNKNOWN_METHOD", "message": "Unsupported method" } }
```

### Event

```json
{ "type": "event", "event": "engine.ready", "payload": { "protocol": "2", "engineVersion": "0.1.0" } }
```

Structured startup failure event:

```json
{
  "type": "event",
  "event": "engine.startupFailed",
  "payload": {
    "stage": "bootstrap",
    "code": "BOOTSTRAP_FAILED",
    "message": "...",
    "paths": { "logFilePath": "/logs/engine.log" }
  }
}
```

Engine exit event, raised by the shell — not the engine — when the engine process is gone (2026-09 production readiness, Slice 5). `status` is the exit code or `null`, `graceful` is true when the shell asked the engine to stop, `generation` is the launch number within this shell:

```json
{
  "type": "event",
  "event": "engine.exited",
  "payload": { "status": 1, "graceful": false, "generation": 1, "pid": 4242 }
}
```

## Lighting Fixture Catalogue Visual Snapshot

`lighting.fixtureCatalog.snapshot` returns engine-owned fixture definitions. The `definition.visual` shape is additive and currently includes:

- physical marker basis: `shape`, `widthMm`, `heightMm`, `depthMm`
- legacy render hints retained for compatibility: `beamAngleMin`, `beamAngleMax`, `fieldAngle`, `pixelLayout`
- fixture identity render hints: `symbolKind`, `symbolVariant`, `emitterLayout`, `output`, `visualConfidence`

Allowed `symbolKind` values are `panel`, `soft-mat`, `linear-bar`, `fresnel`, and `control-node`. Allowed `output.beamType` values are `wash`, `spot`, `fresnel`, `rectangle`, `glow`, and `none`. Allowed `visualConfidence` values are `verified`, `catalogue-derived`, and `fallback`.

`emitterLayout` describes catalogue-owned emitter geometry with `emitterKind`, positive `rows`, `columns`, `segments`, optional `physicalPixels`, and `direction`. `output` describes renderable output metadata with `beamType`, optional `beamAngle`, optional `fieldAngle`, and `photometricSamples`; photometric samples expose `cct`, `distanceMeters`, `lux`, `modifier`, and `source`.

React may render these catalogue fields, but fixture policy, DMX footprints, validation, persistence compatibility, and hardware behavior remain engine-owned.

## Startup Handshake

1. engine emits `engine.ready`
2. shell sends `health.snapshot`
3. shell sends `app.snapshot`
4. shell decides whether the startup target is operator UI or commissioning from `app.snapshot`
5. shell may request non-gating domain snapshots such as `commissioning.snapshot`, `lighting.snapshot`, and `audio.snapshot`
6. shell opens the operator surface only after both startup-gating snapshots succeed
7. shell fails startup if any startup step does not complete inside its watchdog window

In the current scaffold the shell still renders the runtime scaffold immediately, but the protocol and shell state machine now model this startup order explicitly.

## Native Control-Surface Bridge

  - `GET /api/deck/lcd?key=...`: one display
  - `POST /api/deck/light-action`
  - `POST /api/deck/audio-action`
  - `POST /api/deck/camera-action`
  - `POST /api/deck/prompter-action`
- the generated Companion profile now targets this native bridge instead of the Electron web server

- the exported Companion profile (2026-10-03) is Companion 5.0.6's own full export, `version: 12`: layered buttons (`button-layered`) with no top bar, no pressed border and no status icons, an image library with an image of its own for every key and strip cell (120 × 120 and 200 × 100, the deck's own sizes), every option of an action, a feedback or a layer wrapped `{ isExpression, value }`, the generic-http 2.7.0 connection by `moduleId` (`updatePolicy: "manual"`, `lastUpgradeIndex: 1`). The strip taps (`stripTap`) and Del Scene (`deleteScene`) left the profile; the bridge still answers them until a later cleanup. GAIN's switch (`toggleDialMode`) left it too and is refused (`501`, the review of #293). Its triggers: the poll, once a second, one `GET /api/deck/displays` stored as text in the custom variable `deck_raw`; the answer, on a change of `deck_raw`, which keeps it in `deck_displays` only when it carries the bridge's mark (`sse: "deck"`: an error's body, which generic-http stores too, never does) and is newer than the kept one by its `at` (or older by more than 5 s: the hardware link restarted), and sets `deck_age` to `0` by the same rule (the review of #293: an answer the deck does not keep does not count as heard; `>=` there, as the trigger's two actions may run in either order); the age, once a second, `deck_age` one more; and a page-follow trigger for each page, on the page the kept answer names (`jsonpath($(custom:deck_displays), '$.words.workspace') ?? ''`; the review of #293: not the `workspace` line, which goes blank while the link is lost, so a silence of 4 s turned the deck to the app's page when the link came back) — `lighting` brings the deck to page 1, `audio` to page 2, `cameras` to page 3 and `teleprompter` to page 4; Setup has no page, so the deck stays where it is while Setup is open. A follow trigger names the deck (`streamdeck:<serial>`; `self` names no surface in a trigger) when the export found it, else `self`. An expression variable a line (`deck_<display>` for a word or a value, `deck_<display>_head` for the line above it) reads it out of `deck_displays` with `jsonpath(…) ?? ''`; from 4 s without an answer of the bridge's own every line reads `''` and `deck_link` reads `lost`, and every key and cell is grey. A key's or a dial's press posts to its page's route and reads every display again (two requests); the page keys post nothing. The colours follow the bridge's state words with exact equality (internal `check_expression` feedbacks)
- authentication (2026-09 production readiness, Slice 2 — F01): every request must carry `Authorization: Bearer <token>`. The token is `<app-data>/control-surface.token` — 64 hex characters the engine creates from OS randomness on the first launch of an install and reuses afterwards. The exported Companion profile carries the token in the generic-http `header` option of every action, the poll trigger included, so a profile exported before this landed is refused and must be exported and imported again.
- refusals, checked before the body is parsed: no or wrong token → `401` with `WWW-Authenticate: Bearer`; any `Origin` header → `403`; a `Host` other than `127.0.0.1:<port>` or `localhost:<port>` → `400`
- limits (F06): headers over 8 KiB → `431`; a body over 16 KiB (by declared `Content-Length`, before it is read) → `413`; a `POST` without `Content-Length`, or any `Transfer-Encoding` → `411`; a request that has not fully arrived 1 s after a worker picked it up → `408`; four worker threads with a queue of ninety-six connections (sixteen until 2026-09-22: sixteen refused part of the exported profile's once-a-second LCD poll; sixty-four until the CAMERAS and PROMPTER pages, whose displays took the deck's worst instant from 44 requests to 62, and 64 since the LIGHTS page's `OFF?` and `DEL?`; since 2026-10-03 the poll is one request and a press two, so the worst instant is 3), a connection beyond that → `503`. Since fix D (2026-10-02) a worker reads a connection before it answers it: a key's `POST` is answered at once, while a display's read (`GET /api/deck/displays`, `GET /api/deck/lcd`) is parked until no connection waits unread, or for 250 ms at most, so a press waits only for the reads the workers are already answering, not for the rest of the poll that came before it. A connection that finds the queue full goes to the overflow thread, and while any connection waits there every connection does, in the order they came. It is looked at for 50 ms: a `POST` takes one of sixteen slots kept for presses; anything else, and a press once the sixteen are taken, is answered `503`. Every answer is followed by a drain of 250 ms at most, in which the bridge reads what the client still sends, so the client gets its status rather than a reset. Past 128 connections waiting for the overflow thread a connection is closed unanswered, logged as `closed a connection unanswered` and counted with the refusals. `engine.log` gets one `INFO` line a minute, `Stream Deck bridge, the last minute: …` (what was served, the longest wait for a worker and the longest request, the most that waited, what was turned away or timed out), for a minute with a refusal, a timeout or a wait or request of 50 ms or more, and for every minute in which the prompter played. Refused requests are logged at most once per status per minute, and each such line counts the refusals it stands for; a request whose answer could not be written (the client closed the connection) is logged at most once per kind of failure per minute, and the next line of that kind counts those between (2026-10-01). A key a page refuses — a `POST` to one of the four key routes that is not answered `200` — is a `WARN` line of its own (2026-09-28): `Stream Deck key <route> <action> [<value>] was refused (<status>): <sentence>`, one a second at most for each route and action (a dial's turn is many detents); the next line of that route and action counts the refusals between. The displays' reads are not logged. The bridge counts a key's moment from when its connection arrived, not from when a worker took it.
- query parameters are percent-decoded (`%2F` → `/`, `+` → space) before the key lookup (F28)
- lighting keys (2026-09 production readiness, Slice 10 — F12): every `POST /api/deck/light-action` runs under the engine's lighting state lock and changes lighting state only through the functions the IPC lighting requests run — `toggleLight`, `intensityUp` / `intensityDown`, `cctUp` / `cctDown`, `resetIntensity` and `resetCct` through the fixture update, `allOn` / `allOff` through the all-power request, `recallScene` through the scene recall, `saveScene` through the scene create (the deck names the scene `Scene N`; the id follows the scene-create rule), `deleteScene` through the scene delete. `allOff` and `deleteScene` ask first (2026-09-28), as the CAMERAS page's `rec` asks its stop: the first press arms and answers `{ did: "armed" }`, and the key's display (`light_key_off`, `light_key_del`) reads `OFF?` or `DEL?` for 3 s; a second press, 350 ms later at the earliest and within the 3 s, acts and answers with `did: "switched"` or `"deleted"`. An arm is about what it would act on — the scene the deck has selected, and whether the preview is on — and a second press about anything else ends it and answers `{ did: "kept" }`, as does a press sooner than 350 ms after the arm or the act. One key is armed at a time, and any other key of the page ends an arm. The arm lives in the hardware link's memory, for each saved data; a start has none. An armed or kept press raises no event and leaves no row. The preview buffer is the one `lighting.editor.previewMode` switches on: while it is on, a key stages its change there and the light output does not move. The relative keys start from the previewed value while previewing, otherwise from the stored value with a running fade sampled at that moment. Replies of the value, all-power and recall keys carry `preview: true | false`; a value key's reply carries what was stored. `cctUp` / `cctDown` move 200 K inside the selected fixture's own colour temperature range (its definition and mode, as the Lighting plate's slider), and `resetCct` sets the middle of that range rounded to 100 K, as the plate's Reset does: 4400 K on the Astra Bi-Color, 6000 K on the INFINIMAT and the INFINIBAR (2026-10-05; until then a turn stayed inside 2700–6500 K whatever the fixture, and a push set 4500 K). `recallScene` fades as the Lighting page's recall does (2026-10-03, the owner's answer to question 5; until then it always recalled at once): over `lighting.snapshot`'s `recallFadeMs`, and at once into the preview, as the page loads the preview. The deck's scene selection (`selectNextScene`, `selectPrevScene`, `saveScene`) is its own, apart from the screen's `selectedSceneId`.
- events (Slice 10): a successful `POST` raises the event the matching IPC request would — `lighting.changed { reason: "control-surface" }` from `/api/deck/light-action`; `/api/deck/audio-action` raises `audio.changed { reason: "control-surface" }` as before. `/api/deck/camera-action` and `/api/deck/prompter-action` raise what the matching request's reply carries, with its own reason: `cameras.changed { reason, camera }`, `prompter.changed { reason, anchor }`, and `app.changed { reason: "health" }` after them when a lamp says something else. A key of the LIGHTS and CAMERAS pages raises its events once its last event is stamped and its row written, so a page that reads on the event finds the row. A key of the PROMPTER page writes no row, and its last event is kept in memory, not written, before its events are raised (2026-10-02: a turn of the dial waits for no disk). The AUDIO page's keys announce themselves inside their action. A refused action raises nothing of its own, and neither does a `GET`. The read that comes before a key, and the one that fills the CAMERAS page's displays, announce what they find, as the read before any request does: `cameras.changed` with `reported`, `unreachable` or `reachable` for what a camera did itself. - the AUDIO page: `POST /api/deck/audio-action { action, value? }`. `setMixTarget` writes the saved mix target, as the screen's does, with `main`, `phones-a`, `phones-b` or (2026-10-03, the deck's `PHONES`) `phones`, the next phones mix: Phones 1 from Main Out, Phones 2 from Phones 1, Phones 1 from Phones 2; nothing goes to TotalMix. `dialTurn` with `<strip>:up` or `<strip>:down` rides the strip's level into the mix target (the output's own level on `outputs`), 0.01 of the fader a detent and five times as far on a fast turn, whatever dial mode is saved (2026-10-03: until then a saved gain mode rode the preamp gain); `dialPress` mutes; `cycleBank`, `dimToggle` and `soloClearAll` as their names say. `stripTap` is still answered, for no key of the profile. `PHONES` dwells as `PLAY` does (the review of #293): a second `setMixTarget` with `phones` sooner than 350 ms after the one that acted is the same press, answered `{ ok: true, did: "kept" }`, and the mix target stays; the other values do not dwell. `toggleDialMode`, the old profile's GAIN key, is refused (`501`) since the review of #293, and the dial mode reads `fader` wherever it is reported (the context's `dialMode`, `audio_state_mode`), whatever an older build saved
- the CAMERAS page (D14; 2026-09-28): `POST /api/deck/camera-action { action, value? }` runs under the cameras' lock, through the functions the `cameras.*` requests run. `select` with `1`, `2` or `3` is `cameras.select`. `bank` puts the dials on the next of `exposure`, `colour` and `focus`. `dial` with `<dial>:up` or `<dial>:down` (the dial `1` to `4`) is one of the camera's own steps on the selected camera, of the setting the bank gives the dial; a dial with nothing to set in the bank is refused (`409`). `dialPush` with the dial is a one-shot autofocus for dial 1 on the focus bank, and refused (`409`) otherwise. `rec` acts on CAM 1 whichever camera is selected: one press starts; while CAM 1 records a press arms the stop and a second, 350 ms later at the earliest and within 3 s, stops. ## Startup Lifecycle States

The shell startup state machine currently uses these lifecycle states:

- `idle`
- `launching-process`
- `waiting-for-ready-event`
- `waiting-for-health-snapshot`
- `waiting-for-app-snapshot`
- `ready`
- `failed`

Contract rules:

- `engine.ready` means the engine process is alive, storage bootstrap completed, and the protocol version is compatible enough to continue startup.
- `health.snapshot` provides operational readiness and diagnostics metadata.
- `app.snapshot` provides engine-owned shell state, UI-routing state, and startup gating data such as workspace/window restoration, commissioning status, and startup target surface.
- `app.changed` is a non-startup domain event used to tell the shell that app-owned routing or commissioning state mutated and snapshots should be refreshed. With `reason: "health"` it reports a change in the engine's health status (2026-09 production readiness, Slice 8): a subsystem in `health.snapshot`'s `checks.engine` changed state — the Stream Deck bridge port, a TotalMix meter port, the light-output socket, the database backups or the storage check. It is raised on a change of state only, never for a first `ok` and never for a repeated state. Since the new pages program's Slice 5a it is also raised after a `prompter.*` request that changed `checks.prompter` (Teleprompter › The Prompter XL).
- `commissioning.changed` is a non-startup domain event used to tell the shell that commissioning probe/config state mutated and snapshots should be refreshed.
- `lighting.changed` is a non-startup domain event used to tell the shell that lighting state mutated and snapshots should be refreshed. With `reason: "control-surface"` a Stream Deck lighting key changed it — or the preview buffer — through the local bridge (Slice 10). With `reason: "backup-restored"` an applied archive rewrote it and held the light outputs (2026-09-28). With `reason: "bridge"` the bridge watch's word changed: the bridge stopped answering, answered again, or the watch ended (2026-09-29).
- `prompter.changed` (new pages program, Slice 4) says the Teleprompter changed: `{ reason, anchor }`, where `anchor` is the glass's motion from now on (see "Teleprompter" below) or `null` when nothing is on the prompter. Every `prompter.*` request that changes something raises it with its reason; `reason: "at-end"` says the text stopped at `END`, raised by whoever finds it there first — the prompter's clock, or any `prompter.*` request or PROMPTER key, a read or a refused one included, before its own answer (a display of the deck is not one) — and an applied archive restore raises `reason: "backup-restored"`. A read raises nothing else.
- `audio.changed` is a non-startup domain event used to tell the shell that discrete audio state mutated and snapshots should be refreshed. It is emitted for gain/sends/a TotalMix snapshot load, transport config, clip clear, and other command results, not for high-frequency meter frames.
- `audio.meters` is the high-frequency compact meter feed. Shells must update their meter frame path only and must not refresh `audio.snapshot` for every meter frame. The current compact telemetry payload fields are:
  - `sequence`: monotonically increasing meter-frame number for the current engine process.
  - `monotonicTimestampMs`: monotonic milliseconds since the meter publisher started.
  - `cadenceHz`: intended publication cadence for the compact meter stream.
  - `meteringSource`: `rme-totalmix-osc`, `simulated`, or `disabled`.
  - `meteringState`: `live`, `stale`, `offline`, `simulated`, or `disabled`.
  - `lastPacketAgeMs`: age of the most recent live RME OSC meter packet, or `null` for simulated/disabled metering.
  - `diagnostics`: packet counters and mapping diagnostics, including packet count, mapped packet count, unknown packet count, last received OSC address, and mapped entry count.
  - `selectedMixTargetId`: active mix target id.
  - `channels`: channel meter entries keyed by each entry's `id`.
  - `mixTargets`: output/mix-target meter entries keyed by each entry's `id`.
- Compact meter entries expose normalized fallback values (`meterLeft`, `meterRight`, `meterLevel`, `peakHoldLeft`, `peakHoldRight`) plus live-console dBFS fields (`levelLeftDbfs`, `levelRightDbfs`, `peakLeftDbfs`, `peakRightDbfs`, `rmsLeftDbfs`, `rmsRightDbfs`, `peakHoldLeftDbfs`, `peakHoldRightDbfs`) and status fields (`meterPoint`, `peakWarning`, `meterPointOver`, `meterPointOverLeft`, `meterPointOverRight`, `channelPathClip`, `channelPathClipHold`, `over`, `overLeft`, `overRight`, `clipHold`, `clip`). `level*Dbfs` is the preferred moving meter body; `rms*Dbfs` remains as a compatibility alias. `peak*Dbfs` and `peakHold*Dbfs` are source peak fields; the shell may render an operator-controlled display peak hold from the visible meter body. The default display range is `-60 dBFS` to `0 dBFS`; the shell keeps adjacent marks at `0`, `-6`, `-12`, `-18`, `-24`, `-40`, and `-60`, with `-18 dBFS` as the nominal operating reference.
- Production RME frames use truthful console-style `meterPoint` values: `input` for hardware input/preamp channels, `playback` for software playback channels, and `post-fader` for output/mix-target meters. The engine applies console ballistics before publishing compact frames: held peaks stay fixed for `1500 ms`, then decay at `20 dB/s`; `peakWarning` begins at `>= -3 dBFS`; `meterPointOver*`/legacy `over*` begins at `>= 0 dBFS`; and `channelPathClipHold`/legacy `clipHold` latches until `audio.clip.clear`.
- Production meter frames with `meteringSource=rme-totalmix-osc` are derived only from received RME TotalMix OSC meter packets. The engine clears/freezes meter values and reports `stale` or `offline` when packet age exceeds the live threshold; it must not substitute simulated motion.
- Simulated metering is dev/test only and requires explicit fixture/dev configuration such as `SSE_AUDIO_SIMULATED_INPUT_MODE=1`. Simulated meter frames must always identify themselves with `meteringSource=simulated` and `meteringState=simulated`.
- `settings.changed` is a non-startup domain event used to tell the shell that persisted shell settings mutated outside a direct `settings.update` request and the authoritative `app.snapshot` should be refreshed.
- `support.changed` is a non-startup domain event used to tell the shell that backup/export state mutated and support snapshots should be refreshed.
- `ready` means the shell has received both health and app snapshots, not merely that the process exists.

## Teleprompter

New pages program, Slice 4 (2026-09-27; the ledger's D20, `docs/design/teleprompter.md`). The hardware link keeps the scripts and runs the prompter; the front end draws the glass — the Prompter XL's screen (its window, Slice 5b) and the page's copy of it (Slice 6), one component since Slice 5a — and measures its layout. Every `prompter.*` request runs under the prompter's own lock. A request that changes something answers and raises `prompter.changed { reason, anchor }`; a refused one changes nothing and raises nothing of its own. Every request first stops the text at `END` if it got there, and says so with `reason: "at-end"`.

**Saved data (schema 9).** `prompter_scripts` (each script's paragraphs as JSON, its name, the file it came from, when it was made and changed, its speed and its place, and when it was removed), `prompter_script_versions` (each script's last 20 texts) and `prompter_state` (one row: the look, the take's text size, and what the glass shows — the script and its text as it went on — with the revisions of that text and of the look). The live data's schema 7 goes to schema 9 in one start, behind one pre-migration copy.

**Scripts.** A script is paragraphs of runs: `{ runs: [{ text, bold, italic, underline }] }`. A line break inside a paragraph is `\n` in a run's text. A word is a run of characters that are not white space (`/\S+/gu`). A cue is text in square brackets on one line; a line that holds a cue and nothing else is a jump target, and a word that is all cue is not read aloud, so it does not count towards the pace. The place is `{ paragraph, word }`, both from 0, and `{ paragraph: <paragraph count>, word: 0 }` is the end. Every text that comes in is cleaned: U+FEFF goes, carriage returns and U+0085, U+2028 and U+2029 become `\n`, a tab becomes a space, other control characters go.

**The clock (the slice's first step, answered 2026-09-27: layout units).** The view that draws the glass reports its layout with `prompter.layout.report { layoutKey, lines: [{ paragraph, word, top, height }], endTop }`: every line's paragraph, first word, top and height in the glass's pixels at its 1,920 px width, and where the reading line stands when `END` reaches it. `layoutKey` is the prompter's current key (`g<text revision>-l<look revision>`); a report for another key answers `{ accepted: false }` and changes nothing, and one that does not fit the text on the glass is `INVALID_PARAMS`. The layout is kept in memory only and is reported again after a start. The speed in pixels a second is the pace (words a minute) times the layout's pixels per read word, taken from its full lines of running text (a line another line of its paragraph follows, holding a read word: their heights over their read words), so a full line passes the reading line in its words' time at the pace and the paragraph gaps, the cue lines and a paragraph's last line pass at that speed too, and the time left, from the pixels to `END`, runs a little longer than the words at the pace (2026-10-08, finding 13 of the walk of 2026-10-07; until then the whole height over the read words, which read 22 to 29 % fast). Without a full line the lines holding a read word serve; a script of cues alone is paced by all its words over the whole height. The anchor is:

- `layoutKey`, `place` (the paragraph and the word at the reading line), `wordOffset` (how far into that paragraph the reading line stands, in words: `6.5` is halfway through its seventh word; `place.word` is its whole part), `position` (the reading line in pixels; `null` without the layout), `endPosition`, `pxPerReadWord`;
- `playing`, `atEnd`, `fromWpm`, `toWpm`, `rampMs` (0.3 s eases for play, pause and a new pace);
- `moveFromPosition` and `moveMs` (a jump's 0.2 s move on the glass; the place is the target at once);
- `ageMs`: how old the anchor was when it was sent, since the two processes share no clock.
- `revision` (fix C, 2026-10-02): the anchor's number. It rises whenever the anchor says something new and stays while it does not, whoever asks, so a read of an unchanged glass carries the number the last event did. It is given under the prompter's lock, so a view that holds an anchor takes one with a higher number, keeps its own for an equal one, and drops a lower one, which came late from another thread. It counts within one run of the hardware link: a view forgets it when the link stops (`engine.exited`) and takes the first anchor it reads after `engine.ready` whatever its number.

A view draws `position(t) = min(position + pxPerReadWord · words(ageMs + t), endPosition)`, `t` counting from when the view got the anchor (not from when it first drew it), with `words(t) = (v0·t + (v1 − v0)·t²/(2r))/60` while `t < r` and `((v0 + v1)/2·r + v1·(t − r))/60` after (seconds, words a minute). A view whose layout has another key draws from `place.paragraph` and `wordOffset` — inside a line, the reading line's height is the share of the line's words it has passed — and reports its layout. The same rule carries the place from one layout to the next in the hardware link, so a new size moves the words at the reading line by less than a word. The first report for a key is the one the clock runs on; a later report for the same key (the other view's) answers `{ accepted: true }` and changes nothing. Every paragraph needs a line of its own with a height, an empty one included, or the report is refused. `native/rust-engine/src/prompter/clock/motion-cases.json` holds the cases the hardware link and the front end's copy of the formula (`frontend/packages/engine-client/src/prompter/motion.ts`) are both tested against. The prompter is paused after every start and every archive restore; it stops by itself only at `END`; a new look, a new size or an Update keeps the words at the reading line.

**Reads.**

- `prompter.snapshot` → `{ look, sizePx, glass, scripts, removed, screen }` (`screen`: the Prompter XL as last reported, Slice 5a, below): `glass` is `null` when nothing is on the prompter, else `{ scriptId, name, layoutKey, laidOut, notUpdated, speedWpm, place, paragraphCount, playing, atEnd, timeLeftSeconds, lengthSeconds, estimated, cues, anchor }` (`estimated` while the times come from the words, before a layout); `scripts` are sorted by name with numbers in their natural order and `removed` newest first, each `{ id, name, sourceFileName, paragraphCount, readWords, speedWpm, lengthSeconds, place, atEnd, createdAt, changedAt, removedAt, onPrompter }`.
- `prompter.glass.snapshot` → `{ scriptId, name, layoutKey, paragraphs, look, sizePx, anchor }`: what the glass draws. When nothing is on it, `paragraphs` is empty and `scriptId`, `name`, `layoutKey` and `anchor` are `null`; `look` and `sizePx` are always there.
- `prompter.script.snapshot { scriptId }` → `{ script, paragraphs, cues, versions }`, versions newest first (`{ id, readWords, keptAt, reason }`).

**Scripts' methods.**

- `prompter.script.import { fileName, contentBase64, updateScriptId? }`: a file the page's own file picker read (the slice's first step 2a: a name and its bytes; the hardware link reads nothing from a path). `.docx` and `.txt` are read; a `.doc`, another kind, a password-protected document, a file that is not what its name says, one over 20 MB, over 30,000 words or over 2 MB of text, and one with no text are refused as `PROMPTER_IMPORT_REFUSED` with the operator's sentence (a paste over 20 MB has a sentence of its own). Runs of spaces inside a line come in as one space, and runs of empty lines as one. Answers `{ scriptId, name, sentence }`, the sentence counting what was kept and left out (`Imported Interview intro.docx: 18 paragraphs, 1,240 words, 3 cues. Left out: 2 pictures, 1 comment. Tracked changes were taken as accepted.`). With `updateScriptId` the file's text becomes that script's, its earlier text kept as a version.
- `prompter.script.paste { html?, text? }`: what the page read from the clipboard (first step 3a), as a new script named after its first words. HTML that yields no word falls back to the plain text; a blank line in the HTML (`<br><br>`) ends a paragraph, as in a `.txt`.
- `prompter.paste.convert { html?, text? }` (Slice 6b; the operator's answer of 2026-09-27: keep the formatting): what the editor's Paste read from the clipboard, read as `prompter.script.paste` reads it — bold, italic, underline, paragraphs and headings as cues, the same fallback to the plain text — and refused as it is refused (`PROMPTER_IMPORT_REFUSED`: over the paste's 20 MB, no text, over 30,000 words, over 2 MB of text). Answers `{ paragraphs, sentence }`: `paragraphs` in the shape `prompter.script.edit` takes, for the editor to insert at its cursor and send back whole with `edit`, and the paste's sentence (`Imported the pasted text: 2 paragraphs, 7 words, 1 cue. Left out: 1 picture.`). It converts and answers: it makes no script, keeps no version, changes nothing, raises no event and is not a Recent actions row; the `edit` that follows saves the text, and a script over 30,000 words is refused there.
- `prompter.script.create { name? }` (`New script`, `New script 2`, …), `prompter.script.rename { scriptId, name }`, `prompter.script.edit { scriptId, paragraphs }` (saved as the operator types; an edit of the script on the prompter waits for `prompter.update`; over 30,000 words or over 2 MB of text is `PROMPTER_SCRIPT_TOO_LONG`, as an import's caps are), `prompter.script.remove`, `prompter.script.restore` and `prompter.script.delete { scriptId }` (the script on the prompter cannot be removed: `PROMPTER_SCRIPT_ON_PROMPTER`; only a removed script is deleted for good: `PROMPTER_SCRIPT_NOT_REMOVED`), and `prompter.script.version.bringBack { scriptId, versionId }` (the current text is kept first).

**What the glass shows** (D11: replacing, updating and clearing are armed on the page).

- `prompter.putOn { scriptId, replace? }`: on a blank prompter one press; when another script is on it, `replace: true` or `PROMPTER_REPLACE_NOT_CONFIRMED`. The script comes on paused at its place, or at the top when it was left at its end. Answers `{ action: put-on | replaced, name, replacedName, sentence }`.
- `prompter.update`: the edited text goes on with the same words at the reading line; when the paragraph there was deleted the place moves to the next paragraph's start and the sentence says so. `PROMPTER_UP_TO_DATE` when there is nothing to update.
- `prompter.clear`: the glass goes black; the script keeps its place.

Each is a Recent actions row (`domain: prompter`, with the sentence). While nothing is on the prompter, `PROMPTER_NOTHING_ON` answers `prompter.play`, `prompter.pause`, `prompter.speed`, `prompter.jump`, `prompter.update` and `prompter.clear`; `prompter.textSize` and `prompter.look.update` change the look for the next script, and `prompter.layout.report` answers `{ accepted: false }`. Clear and Replace leave the script the place it was read to — where a pause's ease stops — in its own text when it was edited and never Updated.

**The take** (one press each; none starts the scroll but `prompter.play`).

- `prompter.play` (`PROMPTER_NOT_ON_GLASS` while nothing is drawn on the glass, below; `PROMPTER_AT_END` at the end, until a jump moves the place back; `PROMPTER_NOT_LAID_OUT` before a layout), `prompter.pause` (it saves the place where its 0.3 s ease stops the text). A place or a pace that cannot be saved is a line in the log, never a refused control: the take goes on and the next save tries again.
- `prompter.speed { wpm | step }`: 40–300 words a minute in steps of 5, the script's own; `step` is a number of those steps (`step: 1` is 5 words a minute faster), stopping at the ends.
- `prompter.jump { to, paragraph?, word? }`: `top` (pauses), `back` (the start of the paragraph at the reading line; from its first line, the one before), `nextLine` / `previousLine` (need the layout), `nextParagraph` (`PROMPTER_NO_PARAGRAPH` from the last paragraph), `previousParagraph`, `nextCue`, `previousCue` (`PROMPTER_NO_CUE` when there is none; a cue at the reading line is neither), `paragraph` (from 0) or `place`. A jump keeps the scroll as it was; only `top` pauses.
- `prompter.textSize { sizePx | step | standard }`: 48–160 px in steps of 4, or the look's standard; `step` is a number of those steps (`step: -1` is 4 px smaller), stopping at the ends.
- `prompter.look.update { standardSizePx?, lineSpacingPercent?, marginPercent?, textColour?, readingLinePercent?, readingLineAcross?, dimReadText?, paragraphNumbers? }`: the proposal's §4.1 ranges; the take's size follows a new standard when it was at the standard.

**The Prompter XL** (the new pages program's Slice 5a; first steps answered by the operator on 2026-09-27). Only the shell reads Windows' display configuration, so the shell reports what it found — at its start, at every look at the screens (once a second) and at once after the hardware link has started — and the hardware link works out the state and owns what follows from it. The shell keeps the window on the Prompter XL, and reports the screen as found without a `windowError` only while that window's page tells it, once a second, that it draws: a report that the screen is there unlocks `prompter.play`.

- `prompter.screen.report { found, duplicated?, width?, height?, refreshHz?, windowError? }`, sent by the shell, never by the page (the shell's page request path, `engine_request`, refuses it): whether Windows sees a screen named `Prompter XL`; whether it shows a copy of another screen; its size, numbers above 0 kept in whole pixels (required when found); its refresh rate, optional, kept in whole hertz (Windows gives a fraction: 59.94 is 60); why the window on it does not show (it could not be opened, it does not stand on the Prompter XL, or its page does not draw), a sentence trimmed and cut at 300 characters, ignored while duplicated. `found: false` ignores the rest, and anything else is `INVALID_PARAMS`. It answers `{ screen, paused }`. The state is `not-connected` (not found), `duplicated`, `not-showing` (a `windowError`), `low-resolution` (below 1920×1080) or `connected`, in that order. The report is kept in memory only: after every start the Prompter XL is `NOT CONNECTED` until the shell reports (first step 2), with a sentence of its own that says Windows has not reported it yet. A report the same as the last raises nothing; one that differs (its state, size, refresh rate or window reason, or the first since a start) raises `prompter.changed { reason: "screen" }`. The shell sends it at every look at the screens, so a report lost to a moment's failure is repaired by the next; while the window opens for the first time it sends none, and the hardware link keeps what it had. The prompter's window itself sends `prompter.glass.snapshot` and `prompter.layout.report` and no other request: the shell refuses it the rest.
- `prompter.play` is refused as `PROMPTER_NOT_ON_GLASS` while nothing is drawn on the glass — `NOT CONNECTED`, `DUPLICATED` or `NOT SHOWING` — with a sentence for each; `LOW RESOLUTION` plays. It is checked after `PROMPTER_NOTHING_ON` and before `PROMPTER_AT_END`. A report that takes the glass away while the text scrolls pauses it (its 0.3 s ease; the place saved where the ease stops, `paused: true`), and a report that brings it back leaves it paused (D12). Jumps, speed, the text size, the look and edits keep working.
- `prompter.snapshot` carries `screen`: `{ state, word, tone, reported, draws, width, height, refreshHz, windowError, sentence }`, the words `CONNECTED`, `NOT CONNECTED`, `DUPLICATED`, `LOW RESOLUTION` and `NOT SHOWING`, the tone `ok`, `attention` (`LOW RESOLUTION`) or `error`.
- `health.snapshot`'s `checks.prompter` is `{ ok, status, word, summary, notUpdated, screen }`: the worse of the screen's state and `NOT UPDATED` (first step 3; at the same tone `NOT UPDATED` wins over `LOW RESOLUTION`), the word and the sentence of that state, whether the script on the glass was edited after it went on, and `screen` as above. Only a Prompter XL state the shell has reported counts toward the whole `status`, and as `attention` at most (first step 1, and the operator's answers after CI's qualification lane and at the review): an unreported Prompter XL and `NOT UPDATED` light the lamp only. When one counts, the top-level `summary` ends with `Prompter: ` and its sentence. After a request that can change the check (`prompter.screen.report`, `putOn`, `update`, `clear`, `script.edit`, `script.rename`, `script.import`, `script.version.bringBack`) and did, or whose check could not be read, `app.changed { reason: "health" }` follows the request's own `prompter.changed`, so the header's lamp follows. A take's controls never read it, and it never fails a request.

## Cameras

New pages program, Slice 8 (2026-09-27; the ledger's D10–D15, D17–D19; its first steps answered by the operator the same day). The hardware link keeps the three cameras — who holds each, what each reports, one selected camera — and is the only thing that talks to them; the page (Slice 9) and the deck (Slices 7 and 12) draw and send what it answers. Every `cameras.*` request runs under the cameras' own lock. A request that changes something answers and raises `cameras.changed { reason, camera }`; a refused one changes nothing and raises nothing of its own.

**The three cameras** are fixed: `1` is CAM 1, the Blackmagic Pocket Cinema Camera 6K Pro, over Bluetooth; `2` and `3` are CAM 2 and CAM 3, Panasonic LUMIX BGH1s, over the network. A camera is set up once Setup holds it: CAM 1 once it is paired (with the operator present, the camera showing its PIN; D15 rule 2), CAM 2 and CAM 3 once their address is entered (D15 rule 1). New saved data holds none, so a fresh start contacts nothing.

**The link.** Each camera's link is the real one — CAM 1's in Slice 11 (Blackmagic's Bluetooth protocol), CAM 2's and CAM 3's in Slice 13 (Panasonic's LUMIX SDK) — or the simulated one, which every test, lane and scratch run uses (`SSE_CAMERAS_SIMULATED=1`, which the lanes set and check; D15 rules 1–2). CAM 1's real link is built on Windows (the Pocket's link, 2026-10-06; parts 2 to 7): Windows' own pairing and GATT, behind a guard that no test and no plain development run passes (D15 rule 2; `npm run app -- --bluetooth`, D41, is the attended exception). Until Slice 13 a build without the simulated link has no link to CAM 2 and CAM 3 (the studio's build; a development build simulates the cameras), nor to CAM 1 where there is no Windows (the Linux builds of CI). Setup then takes no pairing and no address (`CAMERA_NO_LINK`, below), so such a camera reads `NOT SET UP` with a sentence that says Studio Control has no link to it yet, and lights the Cameras lamp only. A camera the saved data holds all the same (a database backup restored whole brings what it holds) is set up and reads `UNREACHABLE` with that sentence, until its address is taken away (CAM 2, CAM 3) or it is forgotten (CAM 1, whose pairing such a backup can hold). The simulated cameras live inside the hardware link and touch no network and no radio; they report what board 2 assumes (the slice's first step 4): CAM 1 every value D10 lists but a focus position (its EF lens reports none), with a battery and a record time (since 2026-10-08), CAM 2 and CAM 3 no tint, focus position, ND, dynamic range or display LUT, and no recording. The drift guard: in a test build the real network link refuses any camera address that is not on this PC (`127.0.0.1`, `::1`, `localhost`) before it would connect (D15 rule 1).

**Holding (D13).** Studio Control holds every set-up camera whenever it runs: it reads the camera and sends only what the operator presses. Starting, opening the page, taking a camera back, restarting and restoring a backup send nothing to a camera; the camera wins a disagreement (D12), and a value it changes itself (on its body, or from another controller) comes back as `cameras.changed { reason: "reported" }`. The hardware link reads every held camera again before each `cameras.*` request, so a change on the body, a camera that stops answering (`unreachable`) and one that answers again (`reachable`) are said then; the real links (Slices 11 and 13) add a watch that notices them between requests. `cameras.release { camera, confirm: true }` lets a camera go, to LUMIX Tether (CAM 2, CAM 3) or to nobody (CAM 1, whose other controller may then take it; `CAM 1 released.`): the hardware link stops reading it and sends it nothing, and its values are no longer shown (press twice on the page, D19: without `confirm: true` it is `CAMERA_CHANGE_NOT_CONFIRMED`). A recording CAM 1 released goes on recording; only the camera stops it then. `cameras.connect { camera }` takes it back and reads it again. A release is kept (D41, 2026-10-06): after a start a released camera is still released, until `cameras.connect`; `cameras.setup.forget`, a new address and a new pairing end it too. It is saved as a setting of its own (`cameras.released.<camera>`), not in the camera's row, so a database backup restored whole brings it back and an archive does not carry it. The selection and the dials' bank are kept in memory. (Until D41 a start held every set-up camera again.)

**The state** of each camera: `not-set-up` (`NOT SET UP`, attention), `held` (`HELD`, ok), `released` (`RELEASED`, attention) or `unreachable` (`UNREACHABLE`, error: a held camera that does not answer; D19), each with its sentence. An unreachable camera keeps the values it last reported, with the time it last answered (`readAt`), and the page shows them as doubt; a released or never-read camera has none (after a start with a saved reading, the saved values as the last read: `valuesLastRead`, below).

**The selection** (D19). One camera is selected — the big picture, the plate and the deck's dials all set it: `cameras.select { camera }`. It is kept in memory; after a start it is CAM 1. Selecting sends nothing to a camera, and selecting the camera already selected raises `cameras.changed { reason: "select" }` all the same. Selecting is not a Recent action.

**The dials' bank** (D14). The Stream Deck's four dials set the selected camera, and the bank says what: `exposure` (ISO, shutter, iris, ND), `colour` (white balance, tint) or `focus` (focus). `cameras.bank.set { bank }` sets it from the page, and the deck's `BANK` key goes through the three in turn; both raise `cameras.changed { reason: "bank", camera: null }` and answer `{ bank, dials }`. It is kept in memory, as the selection is; after a start it is `exposure`. `cameras.snapshot` carries it as `dials: { bank, sets }`, `sets` the setting each dial sets, left to right, by its name in the requests, `null` for a dial that sets nothing in the bank. Setting the bank sends nothing to a camera and is not a Recent action; any other word is `INVALID_PARAMS`.

**What a camera reports** (D10). `cameras.snapshot` answers `{ selected, dials, cameras: [camera, …], pictures, recent }`, each camera `{ camera, tag, model, link, setup, state, word, tone, sentence, readAt, valuesLastRead, values, auto, focusSteps, recording, battery, picture }`:

- `setup`: `{ setUp, address, paired, vmixInput, vmixOutput, noLink, pairing }` — the address (CAM 2, CAM 3; `null` until entered), whether CAM 1 is paired (`false`, with `setUp`, while the link finds its pairing gone: below), the vMix input saved for the camera (1–3 until `cameras.setup.update` changes it; the simulated test pictures stand in for inputs 1 to 4, and Setup no longer offers it), the vMix output its picture comes from, fixed (D31: CAM 1 Output 2, CAM 2 Output 3, CAM 3 Output 4), `noLink`: the sentence that says why Setup can pair or take no address in a build with no link to the camera (`CAMERA_NO_LINK`'s own), `null` when it can; and `pairing`: CAM 1's pairing, `{ state, sentence }`, while one runs or when the last one failed, `null` otherwise and always for CAM 2 and CAM 3 (Setup, below).
- `valuesLastRead` (2026-10-08, finding 19 of the Pocket's attended run): `true` for a held camera whose values are what it last reported, at `readAt`, not what it reports now: its link has brought no setting since it connected (a start, where the last reading comes from the setting `cameras.lastReading.<camera>`; a quick reconnect; a `Connect` soon after a `Release`), and the Pocket sends its settings again only after some minutes without a controller or a power-on. The page shows the values as doubt, `last read`, with the time, until the camera reports a setting; one setting reported clears the mark for all (a per-setting mark is a roadmap line). While the mark stands, `cameras.set` of a white balance, a tint, a resolution or a frame rate answers `CAMERA_VALUE_NOT_ALLOWED` with a sentence (the display LUT's would too, but CAM 1's LUT is refused as read-only before that), since the other half of the pair would go with it as a guess (D12); the deck's `camera_state_dials` reads `doubt` and `camera_state_rec` `last-known` for a take the kept reading says is running.
- `values`: each setting as the camera reports it, or why not. A choice (`iso`, `shutter`, `iris`, `nd`, `resolution`, `frameRate`, `dynamicRange`, `displayLut`) is `{ reported, value, options, notReported }`: the value and the values the camera allows, in the camera's own words (`400`, `180°`, `1/50`, `f/2.8`, `2 stops`, `6K`, `25`, `Film`, `Film → Ext. video`); a frame rate the camera does not allow at the current resolution is listed in `frameRate.unavailable` with its reason (`not at 6K`). A level (`whiteBalance` in kelvin, `tint`, `focus` from near 0 to far 1) is `{ reported, value, min, max, step, unit, notReported }`. `displayLutOn` is `{ reported, value, notReported }`. `displayLutLock` (2026-10-08, finding 16) is the sentence why the camera takes no change to its display LUT though it reports it (CAM 1 takes none over Bluetooth: the LUT is the camera's own menu's; `cameras.look.set` of it answers `CAMERA_VALUE_NOT_ALLOWED` with the sentence), `null` when it takes one; CAM 1's `focus` is not reported (finding 15): its EF lens reports no position and takes none. When `reported` is false, `value` is `null` and `notReported` says why in the camera's own terms (`The BGH1 has no ND filter.`, `CAM 2 does not report tint.`).
- `auto`: the one-shot autos the camera offers (`focus`, `whiteBalance`, `iris`); `focusSteps`: whether focus moves nearer and farther without a reported position (the BGH1s).
- `recording`: `{ records, recording, timecode, timecodeReported, startedAt, cardTimeLeft, cardTimeNotReported }` — CAM 1 alone records (D10, D14); `startedAt` is when the hardware link saw the take start (`null` when the take started before it looked, or while the camera did not answer: the take may have stopped and started again in between); `cardTimeLeft` is the record time left on the camera's media as CAM 1 reports it (2026-10-08: the Pocket's 9.2, one number per slot, summed, `17 h 00 min`), `cardTimeNotReported` why there is none though the camera was read (it reports no record time left: no medium, or a full one, the protocol does not say); `battery`, beside `recording`, is the battery as CAM 1 reports it (9.0: `100 % · on mains`, `63 % · charging`, the voltage when the camera shows it), `null` for a camera that does not report one or is not shown. Neither counts as a setting reported (`valuesLastRead` stands until one is), nor as a change the camera made.
- `picture` and `pictures`: below, under **The pictures**.
- `recent` (the Cameras page's Recent list): the action log's five newest rows about the cameras (`domain: cameras`), newest first, each `{ id, at, source, action, target, detail }` as it was written: `source` is `ui` (the screen) or `deck`, `target` the camera's tag, `detail` the sentence. `null` when the action log could not be read: that never fails the read. Reading leaves no row and raises no event.

**The pictures** (D17, D28). Each camera's picture comes over NDI from vMix on this PC, from its own vMix output (D31; the simulated source's, from the vMix input saved for it), and not from the camera's link: a camera that is released, not set up or does not answer keeps its picture. `picture` is `{ state, word, tone, detail, sentence, advice }`: `state` is `showing` (`LIVE`, ok), `missing` (`NO PICTURE`, attention: the source sends pictures, and none for this input) or `no-pictures` (`NO PICTURE`, attention: no picture arrives at all); `detail` says what arrives, as the page prints it (`test picture`), `nothing received`, or why nothing can (`not started`, `no picture program`); `sentence` says why no picture arrives, in its place on the page (`vMix is not sending CAM 2 over NDI.`), and `advice` what to check under it; both are `null` while it arrives, and `advice` when there is nothing to check. `pictures` is the three together, `{ state, word, tone, sentence, source, note }`: `showing` while every picture arrives (`word` and `sentence` `null`); `missing` (`PICTURE MISSING`) when some do not, its sentence about the selected camera when its picture is missing, otherwise the first whose picture is (`vMix sends no picture for CAM 2. Check that vMix input 2 is still there and live.`); `no-pictures` (`NO PICTURES`) when none arrives. `source` names where they come from (`test pictures`, `vMix Outputs 2 to 4`, `not started`), and `note` is the Pictures section's fine print. The studio's build with the real cameras, and a development run with the simulated cameras, have **the pictures helper**, a process of its own that the hardware link starts below normal priority, tells each camera's vMix input, hears at least once a second, starts again when it ends or stays silent for 5 s, and stops; what the helper says it receives is what `picture` says, and while it starts (`The pictures are starting.`), restarts (`The pictures stopped. Studio Control starts them again.`) or is missing from the build or not its own, `pictures` is `no-pictures` with that sentence. A run with neither the helper nor the simulated cameras (a development build with the real cameras) reads `no-pictures`, `not started`. A change of what it says raises `cameras.changed { reason: "pictures", camera: null }` and `app.changed { reason: "health" }`. In a development run the helper's source is simulated: test pictures on vMix inputs 1 to 4, so a camera on another input reads `missing`. In the studio's build (D34), and in a development run started with `npm run app -- --vmix-pictures` (D33), a hardware test the owner attends, its source is vMix's Outputs 2, 3 and 4 over NDI instead, CAM 1 on Output 2, CAM 2 on Output 3 and CAM 3 on Output 4: `source` reads `vMix Outputs 2 to 4`, a picture's `detail` names its output with its size and rate (`vMix Output 2 · 3840 × 2160 · 29.97`), and every other detail names its output first (`vMix Output 4 · nothing received`), a missing one names the output to check, `no-pictures` says that vMix sends none of the three and what to check, and a helper that takes nothing from vMix says why (`not taken`, `NDI not loaded`). With the simulated cameras and no helper (the engine's unit tests, a studio build's lanes) the same rule stands in for it; the helper's word counts for the input it was told, so until it answers a changed input no picture is claimed for that input. A vMix input changes with `cameras.setup.update` (no page sends it now), which raises `cameras.changed { reason: "setup" }`, and reaches the helper, as the selection does.

**The pictures' link** goes from the helper to the shell and never through the hardware link (D30). At each start the shell opens a listener on 127.0.0.1 with a new secret and puts both into the hardware link's environment (`SSE_PICTURES_LINK`, `SSE_PICTURES_SECRET`); the hardware link clears the secret from its environment and hands both to the helper on its stdin. While the Cameras page shows the pictures the helper connects, says the secret and then its process, and is handed a composition surface that the shell keeps over the page. The helper draws the pictures into it itself, in step with vMix's frames (the test cards 29.97 a second on its own clock), where the page says they stand (the shell's `pictures_place`, the main window only), with the aids each shows (the big picture's guides, zebras and peaking, the loupe's zebras and peaking) and where the loupe looks on the big picture: no picture passes the shell, the page or the hardware link. `cameras.pictures.showing {}` says that the page shows them; the page sends it once a second while it is open, and the helper keeps its link until 30 s after the last. It answers `{}`, raises no event and changes nothing a camera holds. The secret reaches neither the page nor a log.

**Setting a camera** (D11). One press, on a held camera:

- `cameras.set { camera, setting, value }` for `iso`, `shutter`, `iris`, `nd` (a value from its `options`) and `whiteBalance`, `tint`, `focus` (a number in the range, on its step).
- `cameras.step { camera, setting, step }` for the same settings (the deck's dials, the page's steppers): `step` is a whole number of the camera's own steps from −1000 to 1000, not 0 (`INVALID_PARAMS` otherwise), stopping at the ends; `focus` on a camera with `focusSteps` moves it nearer (`-`) or farther (`+`) without a position. A step starts from what the camera reports (2026-10-06): from a value that is not on its list, or a level between two of its steps, it moves from the nearest listed value in the step's direction; a setting the camera has not reported, or reports with no number in it (`Auto`), is `CAMERA_VALUE_NOT_ALLOWED`, since a step has nothing to start from.
- `cameras.auto { camera, what }`: a one-shot `focus`, `whiteBalance` or `iris` the camera offers.

Armed on the page (press twice), and `confirm: true` here or `CAMERA_CHANGE_NOT_CONFIRMED`:

- `cameras.format.set { camera, resolution?, frameRate?, confirm }`: a frame rate the camera does not allow at the resolution is `CAMERA_FORMAT_NOT_ALLOWED`.
- `cameras.look.set { camera, dynamicRange?, displayLut?, displayLutOn?, confirm }`: the picture profile and the display LUT.
- `cameras.record.stop { confirm }`. `cameras.record.start` is one press. Both act on CAM 1, whichever camera is selected (D14): `CAMERA_ALREADY_RECORDING`, `CAMERA_NOT_RECORDING`.

`cameras.set`, `cameras.step` and `cameras.auto` answer `{ camera, setting, value }`, the value as the camera now reports it (`null` for a BGH1's focus step and for CAM 1's autofocus, since neither has a position to report); `cameras.format.set` and `cameras.look.set` answer `{ camera, sentence }`; the record's start and stop `{ camera: 1, recording, sentence }`; `cameras.release` and `cameras.connect` `{ camera, state, sentence }`; Setup's requests `{ camera, setup }`. A change that moves nothing (the same value, a step at an end) is still sent and still raises its event: the camera answers it. A request for a camera that is not held is `CAMERA_NOT_SET_UP`, `CAMERA_RELEASED` or `CAMERA_UNREACHABLE`, with its sentence; a setting the camera does not report or offer is `CAMERA_SETTING_UNSUPPORTED`; a value it does not allow is `CAMERA_VALUE_NOT_ALLOWED`; `cameras.connect` on a held camera is `CAMERA_ALREADY_HELD`. The checks run in that order — the parameters' shape (`INVALID_PARAMS`), the camera's state, the setting, the value, and last the second press — so a request is refused for the first thing wrong with it. Not offered at all (D11): formatting a card, firmware, a factory reset.

**Setup.** `cameras.setup.update { camera, address?, vmixInput? }`: CAM 2's or CAM 3's address, an IPv4 address of one machine (not `0.0.0.0`, a broadcast or a multicast address; `null` takes it away) or `CAMERA_ADDRESS_INVALID`; the vMix input, 1–1000 (kept for the simulated test pictures; no page sends it now). A blank address, an address for CAM 1, a request that names neither, and `vmixInput: null` are `INVALID_PARAMS`; an address is kept in its plain form (`010.0.0.1` is `10.0.0.1`). In a build with no link to the camera an address is `CAMERA_NO_LINK`, checked after the request's shape and the address's form, and nothing of the request is saved; taking an address away, the vMix input and `cameras.setup.forget` stay. `cameras.setup.pair { camera: 1, pin? }` pairs CAM 1 in two steps (D15 rule 2; 2026-10-06), with the operator beside the camera. Without `pin` a pairing begins, and one that runs starts over: the hardware link listens, actively, for Blackmagic's camera service in the Pocket's advertisement or scan reply (the camera's name is not looked at; D42) for a minute, takes the camera it hears, removes a pairing Windows still holds for it (a pairing is always made afresh), and asks Windows to pair, so the camera shows a 6-digit PIN. With `pin` (six digits, spaces around them allowed; anything else is `INVALID_PARAMS`) it hands that PIN over; with no pairing waiting for a PIN it is `CAMERA_PAIRING_NOT_WANTED`. `setup.pairing` says where it stands: `finding` (`Looking for CAM 1. Switch its Bluetooth on, with no other controller connected to it.`), `pin` (`CAM 1 shows a 6-digit PIN. Enter it here within 30 seconds.`: Bluetooth's pairing gives the PIN about 30 seconds, and a pairing that ends while the PIN is awaited says the PIN was not entered in time), `pairing` (`Pairing with CAM 1…`) or `failed`, with the reason and what to do (`CAM 1 was not found within a minute. …`, `CAM 1 did not accept the PIN. Press Pair CAM 1 to try again.`); nothing of a failed pairing is saved. The answer is `{ camera, setup }` with the step, and each step, the request's or the link's own, raises `cameras.changed { reason: "pairing", camera: 1 }`. A pairing that succeeds saves `paired` and the camera's Bluetooth address in CAM 1's row (never shown: `address` stays `null` for CAM 1), ends a saved release, holds the camera and reads it (`reason: "setup"`); at each connection the link then reads the camera's protocol version, writes the controller's name, `Studio Control`, to the camera (D41) and subscribes; nothing else is written to the camera by itself. The simulated CAM 1 shows its PIN at once (`setup.pairing.state` is `pin` in the first answer) and pairs at its own, `123456`. The pairing is kept in memory: after a start none runs. While a held CAM 1's link finds its pairing gone (Windows no longer holds it, or the row holds no Bluetooth address), CAM 1 reads `NOT SET UP` with the link's sentence (`Windows no longer holds CAM 1's pairing. Pair it again in Setup.`), `setUp` and `paired` read `false` so Setup offers the pairing again, and the row is kept, so a Bluetooth adapter that is off erases nothing. The link's finding is announced as any other change of the link's: `cameras.changed { reason: "unreachable" }` when the pairing is found gone, `reachable` when the camera answers again. `cameras.setup.forget { camera }` takes the address or the pairing away (the vMix input stays), and stops CAM 1's pairing if one runs: the camera is not set up again. Windows' own pairing stays; the next pairing makes it afresh. Setup's requests are not Recent actions.

**Recent actions** (`domain: cameras`, with Screen or Stream Deck): the record's start and stop, the format and the look changes, Release, and Connect when the camera is held again, each with its sentence as the operator read it, its full stop kept (`CAM 1 started recording.`, `CAM 1: 25p → 50p.`, `CAM 2 released to LUMIX Tether.`, `CAM 2 held again.`). `cameras.snapshot` carries the newest of them as `recent`.

**The event.** `cameras.changed { reason, camera }`, `reason` one of `select`, `bank`, `setting`, `format`, `look`, `record`, `release`, `connect`, `setup`, `pairing` (a step of CAM 1's pairing), `reported` (a value the camera changed itself), `unreachable`, `reachable`, `restore` (a backup restored) and `pictures` (the pictures helper says something else); `camera` is `null` when it is about all three.

**Saved data (schema 10).** `camera_setup`, one row a camera: its address, whether it is paired and its vMix input (`1`, `2`, `3` in new and migrated data). The live data's schema 7 (or 9) goes to schema 10 in one start, behind one pre-migration copy.

**The backup (format 7).** An archive carries `cameras`: each camera's address and vMix input; the pairing is Windows' own and stays with this PC. A `.sqlite3` database backup restored whole brings back the `paired` and the Bluetooth address it holds; the link holds them to Windows' own pairing (a pairing Windows does not hold reads `NOT SET UP`, Setup above). A restore writes them and sends nothing to a camera; an archive of format 6 or older leaves the cameras' setup as it is. In a build with no link to a camera an archive's address for it is left out, as Setup would refuse it, and the restore's `detail` names the camera (`CAM 2's address was not restored: Studio Control has no link to it yet.`); an address the saved data holds already is not named, and an archive without one takes the saved one away. An archive that names a camera more than once (only one written by hand does) is read to its last word on that camera. Every applied restore raises `cameras.changed { reason: "restore", camera: null }`, as it raises the prompter's. `support.backup.verify` names the part: `…, with N scripts and the cameras' setup.`

**The health check.** `health.snapshot`'s `checks.cameras` is `{ ok, status, word, summary, recording, cameras: [{ camera, tag, state, word, tone, sentence }] }`: the worst camera's state and sentence, and whether CAM 1 records. While every camera is held and not every picture arrives, the pictures' word and sentence stand there instead (`PICTURE MISSING`, `NO PICTURES`, attention): they light the Cameras lamp only. A held camera that does not answer takes the whole `status` to `attention` at most (the slice's first step 3), and the top-level `summary` then ends with `Cameras: ` and its sentence; a camera not set up or released lights the Cameras lamp only. After a request or a link change that changes the check, `app.changed { reason: "health" }` follows `cameras.changed`.

## Ownership

- The shell owns process supervision, retry behavior, and desktop presentation.
- The engine owns persisted application state, commissioning state, and UI-routing decisions derived from persisted state.
- React does not issue raw protocol messages directly. All transport calls go through shell-side adapter methods.
- The shell may cache snapshot data for rendering, but the engine remains the source of truth.

## Versioning

- Additive changes inside existing result objects are allowed in protocol v1 if old clients can ignore the new fields safely.
- Removing fields, changing field types, or changing startup sequencing requires a protocol version bump.
- Protocol 2 (2026-09, the new pages program's Slice 2): Planning's methods, its event, its fixture ids and its snapshot fields are removed, and the backup archive format moves to 5. The contract and this document keep their `v1` file names; the version they carry is `2`. A window and a hardware link of different versions stop at the start with `PROTOCOL_MISMATCH`. Protocol 2 also removes `storage.importLegacyDb` and the `legacy-db-json` restore source (the new pages program's Slice 2b, 2026-09-25 — D3): protocol 2 had not shipped, so the removal rides in it rather than in a protocol 3. The same holds for `dev.parityFixture.load` and the contract's `devParityFixtures`, which no caller had, for the field `updateRepositoryPath` of `runtime.paths`, of `health.snapshot`'s `paths`, of `engine.ready` and of `engine.startupFailed`, which was the installer's (both 2026-09-28), and for talkback (D26, 2026-09-28): `audio.talkback.hold`, the mix targets' `talkback` field, the `talkback` parameter of `audio.mixTarget.update` and the `watchdog` source of `recentEvents` are removed in protocol 2.
- A new startup-critical method required for shell boot must be documented in the startup handshake and treated as part of the versioned contract.

## Error Taxonomy

Structured errors and startup failures should use stable codes grouped by responsibility:

- startup:
  - `BOOTSTRAP_FAILED`
  - `STORAGE_CORRUPT` (the database failed its integrity check or is not a database; the message names the file and the newest database backup; the file is left untouched)
  - `STORAGE_MIGRATION_FAILED` (a schema migration refused a stored value it could not read; nothing was changed and the pre-migration backup is on disk)
  - `ENGINE_ALREADY_RUNNING` (another engine holds the exclusive lock on `<app-data>/engine.lock`; the second engine exits before it opens the database — 2026-09 production readiness, Slice 5)
  - `STARTUP_TIMEOUT`
  - `HEALTH_SNAPSHOT_FAILED`
  - `APP_SNAPSHOT_FAILED`
- process supervision:
  - `PROCESS_ERROR`
  - `PROCESS_EXIT`
  - `ENGINE_BINARY_MISSING`
  - `ENGINE_NOT_RUNNING`
  - `ENGINE_EXITED` (answered by the shell to every request still waiting when the engine process exits; the front-end shows the recovery surface and restarts the engine on its own, at most three times in five minutes — Slice 5)
- protocol:
  - `UNKNOWN_METHOD`
  - `INVALID_PARAMS`
  - `INVALID_ENGINE_MESSAGE`
  - `PROTOCOL_MISMATCH`
- persistence:
  - `STORAGE_ERROR`
  - `RUNTIME_DIRECTORY_ERROR`
- import: none since the new pages program's Slice 2b retired `storage.importLegacyDb`, which answered `IMPORT_SOURCE_NOT_FOUND`, `IMPORT_FAILED` and `IMPORT_REQUIRES_FORCE`
- lighting:
  - `LIGHTING_UNCONFIGURED`
  - `LIGHTING_NOT_VERIFIED`
  - `LIGHTING_PROBE_FAILED`
  - `LIGHTING_SCENE_NOT_FOUND`
  - `LIGHTING_SCENE_RECALL_FAILED`
- teleprompter (new pages program, Slice 4):
  - `PROMPTER_SCRIPT_UNKNOWN`, `PROMPTER_SCRIPT_REMOVED`, `PROMPTER_SCRIPT_ON_PROMPTER`, `PROMPTER_SCRIPT_NOT_REMOVED`, `PROMPTER_SCRIPT_TOO_LONG`, `PROMPTER_VERSION_UNKNOWN`, `PROMPTER_IMPORT_REFUSED`
  - `PROMPTER_NOTHING_ON`, `PROMPTER_ALREADY_ON`, `PROMPTER_REPLACE_NOT_CONFIRMED`, `PROMPTER_UP_TO_DATE`, `PROMPTER_AT_END`, `PROMPTER_NOT_LAID_OUT`, `PROMPTER_NO_CUE`, `PROMPTER_NO_PARAGRAPH`
  - `PROMPTER_NOT_ON_GLASS` (Slice 5a): `prompter.play` while the Prompter XL shows nothing
- cameras (new pages program, Slice 8):
  - `CAMERA_NOT_SET_UP`, `CAMERA_RELEASED`, `CAMERA_UNREACHABLE`, `CAMERA_ALREADY_HELD`, `CAMERA_NO_LINK`
  - `CAMERA_PAIRING_NOT_WANTED` (2026-10-06): a PIN for CAM 1 while no pairing waits for one
  - `CAMERA_SETTING_UNSUPPORTED`, `CAMERA_VALUE_NOT_ALLOWED`, `CAMERA_FORMAT_NOT_ALLOWED`, `CAMERA_CHANGE_NOT_CONFIRMED`, `CAMERA_ALREADY_RECORDING`, `CAMERA_NOT_RECORDING`, `CAMERA_ADDRESS_INVALID`
  - the front end's client throws an `EngineRequestError` carrying the code and the sentence for every refused request, on the live transport and the fixture double alike (Slice 4), so a page can act on a code
- audio:
  - `AUDIO_TRANSPORT_UNAVAILABLE`
  - `AUDIO_NOT_VERIFIED`
  - `AUDIO_PROBE_FAILED`
  - `AUDIO_SYNC_FAILED`, `AUDIO_SYNC_NO_ECHO`, `AUDIO_SYNC_INCOMPLETE`, `AUDIO_GLOBAL_OSC_UNBOUND`
  - `AUDIO_SNAPSHOT_LOAD_STUDIO_ONLY`, `AUDIO_SNAPSHOT_LOAD_FAILED`, `AUDIO_SNAPSHOT_SLOT_INVALID` (2026-10-01, `audio.snapshot.load`)
  - `AUDIO_SNAPSHOT_NOT_FOUND` and `AUDIO_SNAPSHOT_RECALL_FAILED` were the app's own recall's, gone on 2026-10-01; a last action saved with them reads as none

Codes may appear either in engine error responses or shell-generated failure surfaces. The meaning of a code must remain stable once released.

## Design Notes

- JSON Lines is chosen for v1 because it is easy to debug and cross-platform over a supervised child-process boundary
- if binary framing is needed later, preserve the message schema and swap only the framing layer
- the shell should treat `engine.ready` as "process is alive and protocol-compatible", not as "system is fully healthy"
- the engine should bootstrap storage paths before emitting `engine.ready`, so first-launch storage failures are caught before the shell proceeds
- `app.snapshot` is the first non-shell UI-driving contract and exists specifically to keep commissioning/dashboard routing out of ad hoc shell state
